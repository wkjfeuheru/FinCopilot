### 3.10 coordinator/ —— 子 Agent 协调器（决策记录）

**职责**：在**隔离的上下文**中运行子 Agent，只把结论收回主上下文。当前有两个焦点：

- **`risk`**：研报成稿后，用独立的、受限的子 Agent 复核报告的风险与数据支撑，输出修改意见；
- **`general`**：把若干**彼此可隔离的并行任务**分派给子代理（`spawn_agent` 工具），主上下文只收结论、不收过程。

#### 3.10.1 设计决策记录

原设计（v1.1）规划了一个通用 `Coordinator.spawn_agent(task, focus)`，支持 `risk` 与 `macro` 两个焦点。落地路径分两步，决策逐条记录如下：

| 原计划 | 决策 | 理由 |
|---|---|---|
| 通用 `spawn_agent(task, focus)` | **已落地**（2026-09，`general` 焦点） | 当时不做的理由是"只有一个调用方时是空壳；**接口在出现第二个焦点时再抽象**"。第二个焦点（可隔离的并行任务）现已出现，抽象的前提成立，故按既定条件实现——这不是推翻原决策，而是执行它写明的触发条件。实现形态与 v1.1 设想不同：模型提交**一批**任务（`tasks: list[str]`），扇出在一次调用内完成，而非逐次调用 |
| `macro` 焦点（宏观子 Agent） | **明确不做**（能力已具备，仍不实现） | 早先的理由"缺 `web_search` 工具"**已失效**——该工具与研报抓取工具已在 2026-09 落地（§3.4.1）。但**不实现 macro** 这个决定不变：宏观子 Agent 输出的是叙事型判断，无法像风险终审那样锚定到"核对报告数字是否与系统数据一致"的可验证产出，**独立性在这里换不来可检查的正确性**，反而多一个不受控的联网取数路径。若将来要做，应作为独立特性设计，不在本模块 |
| 并行取数作为子 Agent 价值 | **仍不成立**，已由 `asyncio.gather` 覆盖 | 主 Agent 已在同一轮内并行执行多个只读工具。**这一条对通用 `spawn_agent` 同样适用**：派子代理的理由从来不是"快"，而是下面的上下文隔离。注意区分"并行取数"（一个主体的多个字段，中间材料几乎为零 → 同轮 gather）与"逐实体深分析"（多个独立主体，各自取数+核算+判断，中间过程大 → 可扇出）——2026-09 起判据从"是不是取数"细化为"每个单元的中间材料量" |
| 上下文隔离 | **成立，且是唯一不可替代的价值** | 压缩（compaction）只是回收窗口空间，不提供独立视角 |

**因此**：子 Agent 做两件事，两者共享同一个理由——**隔离**。`risk` 靠"没有参与写作"获得独立视角；`general`/`reader` 靠"过程关在子代理里"让主上下文只承载结论。任一焦点都**不**以"并发更快"作为存在理由。

#### 3.10.1.0 三个焦点与编排契约

- **`general`**（**模型可见**，`spawn_agent` 派出的唯一焦点）：任务点名了标的时，子代理**可自行取数**（其工具集即 `general_tool_names()` = `review_tool_names()` + `web_search`），任务要求检索公开讨论时也可联网，再在隔离上下文里完成分析、只回结论。egress 由父会话闸门在派发 general **前确认一次**；已确认则本批 worker 共用父 `PermissionGate`。
- **`reader`**（内部）：只消化交给它的材料、**不取数**。保留在协调器；`summarize_document` **不再**内部派 reader，`spawn_agent` 对外仍只派 `general`。
- **`risk`**（内部）：研报风险终审，可重新取数核对数字；工具集仍是 `review_tool_names()`（**不含** `web_search`）。

**编排契约（模型侧，见 `prompts/system.md`）**：触发扇出时，主 Agent 必须先把请求**拆解/改写为逐单元的自包含任务**（一个实体或一个检索角度一条任务），一次 `spawn_agent` 带全部任务；子代理各自执行后，主 Agent 把结论**汇合**。`spawn_agent` 的输入校验器对"单条任务含 ≥2 个股票代码"做**窄范围硬拒绝**，强制拆解。交叉印证 / 长文档分片是**建议**场景，不强制扇出。

#### 3.10.1.0.1 引擎侧确定性触发（2026-09）

**为什么不能只靠提示词**：`spawn_agent` 的触发如果只写在提示词里，则完全依赖模型自觉。
实测（deepseek-chat）真实用户的自然问法（不会出现"请用子代理"）下，模型倾向于自己串行
取数作答——隐式触发率 0/3；即便把判据改写成硬性指令（"点名 ≥2 实体且要求分别分析即必须
扇出"）也只 1/3。既然"该不该扇出"能从文本**确定性判定**，就把它交给引擎。

**机制**：`shared/fanout.py::fanout_intent(text)` 判定"多实体逐实体分析"——**出现 ≥2 个实体
（6 位股票代码 ∪ 少量辨识度高的行业词）且带有逐实体分析类动词**。命中的请求在 hydrate 阶段
由引擎：预激活 `spawn_agent`（进入本轮 schema），并在 `state` 块末尾下发一条**强制编排指令**
（`_FANOUT_HINT`，放在模型注意力最强处）；同时发 `fanout_routed` 事件。指令在 `spawn_agent`
**成功执行后清除**，避免每轮重复出现而诱导模型反复重派（实测不清会从 3 个子代理膨胀到 12+）。

判据刻意保守：宁可漏判（退回自由裁量的串行作答），也不误判（把"查三家股价"逼成扇出）。
词表刻意剔除"银行/证券/医药"等**会嵌进公司名**的歧义词（否则"招商银行"会被当成两个实体）。
`spawn_agent` 的输入校验器再兜一层：单条任务含多个标的即拒绝。实测强制触发后，自然问法
（"分别评估三家…""对比三家…""分析三家…"）**均稳定扇出且逐实体拆解**，而"查三家股价"仍不扇出。

#### 3.10.1.1 `reader` 焦点：不含取数层

> 2026-09 修订：历史上这里的"通用子代理不含取数层"已不再是全局不变量。现在**模型可见的
> `general` 焦点可取数**（它被派去"分析某实体"时必须能自己取该实体的数据），而**只读材料**
> 这一角色由内部 `reader` 焦点承接。`summarize_document` 不再内部派 reader——它只返回分片
> 索引，由主 Agent 发现 `spawn_agent` 后按片消化（见 §3.10.1.3）。即：把原先单一"通用子代理"
> 拆成"可取数的 general"与"只读材料的 reader"两个焦点。

内部 reader 的工具集是 **`reader_tool_names()` = `{read_file, read_pdf}`**，**刻意不等于** `review_tool_names()`：

- reader **只消化交给它的材料**（**首选直接内联在任务文本里**；已落盘的材料才作为本地路径给出，用 `read_file`/`read_pdf` 读入**它自己的**上下文）。`read_pdf` 属于**读取材料**的能力（按页精读交办的长文档），不是取数能力，故与 `read_file` 并列。
- **未点名标的的处理（general）**：`general` 能取数，但它**只用任务/材料里明确给出的标的与区间**；任务没指明主体时（如"分析一下"），它应**如实回报缺什么**，不得猜一个代码——与"猜代码=重猜而非隔离"的旧约束一脉相承。
- 结构性禁止递归：子代理的 `ToolRegistry(only=...)` 不含 META 组，因此**拿不到 `spawn_agent`**，无法再派生。

#### 3.10.1.3 长文档：索引 + 发现 spawn（`summarize_document`）

`summarize_document`（META 组，**不再** `needs_coordinator`）只做结构感知切分，返回分片索引，**不在内部派生子代理**：

- **切分内核**仍是 `shared/summarize.py`（`split_document` / `document_outline` / `chunk_id`）。每片带稳定 id `P01`…、label、页码或路径、建议任务句。短文低于直出阈值时返回一片。
- **不把分片全文灌进主上下文**。主 Agent **发现** `spawn_agent`（激活 `summarize_document` 时顺带可见）后按片派 `general` worker；任务应是「读 `{path}` 的 P01（约第 x–y 页），聚焦 {question}」，**不要**把全文塞进 `tasks`。主上下文只汇合带 `[P01]` 的结论；也可用 `read_pdf` 按页精读。
- **数字核对不再自动派子代理**。`shared/numbers.py` 的缺口检测可作可选标注；精读补齐由主 Agent 用 `read_pdf` 或按片 spawn 自行决定。
- **`READER_FOCUS` 保留在协调器**（只读材料、不含取数层），但 `spawn_agent` 对外仍只派 `general`。

失败如实：切分或读文件失败时报错，不伪装完整索引。

#### 3.10.1.2 并发下的 citation 归属（修掉一处会出错的设计）

原 `_run_review` 用"跑前记录 cid 集合 → 跑后取差集"判定"本次新增的 citation"。**N 个子代理并发时这是错的**：各自的差集会把彼此的 cid 都算进来，归属必然串号。

修法：`ScopedCitationRegistry`（`data/citation.py`）——子代理仍写**共享**注册表（`cid` 保持连续，这是本节珍视的设计值），但写入经过一层按作用域记录的代理，`register` 时即记下"我铸了哪些 id"，事后无需 diff，**并发安全**。`risk` 焦点同样改用该机制（不再依赖差集）。未改动 `Citation` 结构，故持久化格式不变。

#### 3.10.2 触发点：为什么由 `write_report` 内部触发

复核由 `write_report` 工具**在渲染成功后自动调用**，而不是做成一个模型可选的只读工具。理由：

- **结构性保证**：把触发点放在报告工具内部，"每份报告都被复核"成为系统属性，而不是对模型行为的一个期望。若做成模型可选工具，模型完全可能写完就交付。
- **唯一入口即唯一场景**：只有研报生成会调用 `write_report`，因此"只在研报生成时复核"无需额外约束。

代价：`write_report` 与 coordinator 耦合；模型据意见修订重调 `write_report` 时会再次进入复核路径，故需要**内容哈希闩锁**（见 3.10.5）。

**编排代码的归属（2026-09 重构）**：终审的全部编排——闩锁、coordinator 调用、降级文案、侧车落盘——抽取到 `shared/review.py`（`review_report()` + `ReviewOutcome` + `format_review_lines()`），`write_report` 只剩渲染加一次调用。触发点不变：仍是 `write_report` 内部、唯一入口（曾评估改为 hooks 链上的钩子，被否决——钩子协议是观察者设计，post 无法改写工具结果、无法带独立超时预算、异常会被钩子链吞噬而破坏"未复核必须显眼"的不变量；观察型的审计事件才是钩子的定位，见 docs 03.7.3 的 `review` 行）。终审结局经 `ToolResult.metadata["review"]` 声明给 `AuditHook` 落账。

#### 3.10.3 隔离边界

```
主 AgentLoop
  ├─ WriteReportTool._dispatch                ← 焦点 risk
  │    ├─ ReportPipeline.export()             ← 产出 md/docx
  │    └─ Coordinator.review_risk(topic, 报告正文（截掉附录）)
  │         ├─ 独立 ResearchContext + transcript + SessionStats
  │         ├─ 受限 ToolRegistry(only=review_tool_names())   ← 含只读取数工具
  │         ├─ system = risk_review.md + prompts/risk-checklist.md（判据）
  │         ├─ max_turns = 6
  │         └─ ScopedCitationRegistry → 写共享注册表，cid 连续且归属精确
  └─ SpawnAgentTool._dispatch                 ← 焦点 general（模型可见）
       └─ Coordinator.spawn(tasks=[...])      ← asyncio.gather，N 个子代理并发
            └─ 每个子任务一个子代理：
                 ├─ 独立 ResearchContext + transcript + SessionStats
                 ├─ 受限 ToolRegistry(only=general_tool_names())  ← 只读取数 + web_search
                 ├─ 父会话 PermissionGate（egress 派发前确认一次）或测试替身 ReadOnlyGate
                 ├─ system = prompts/worker.md
                 ├─ max_turns = 8
                 └─ ScopedCitationRegistry → 写共享注册表，cid 连续且归属精确
  └─ SummarizeDocumentTool                    ← 只返回分片索引，不派子代理
       └─ shared/summarize.split_document / document_outline
            └─ 主 Agent 随后可 spawn_agent（general）或 read_pdf 按片消化
```

- **共享 `cite`**：子 Agent 产生的 citation 自动续号（`cit_%06d`），因此进同一份溯源表；写入经 `ScopedCitationRegistry` 记录归属（见 §3.10.1.2）。风险终审的取数由报告工具使用，报告附录只收录 outline 中引用过的 cid，且附录在复核前已渲染完成，故复核的取数**不会污染已交付报告的附录**。
- **`store=None`**：子代理运行是一次独立事件，不写对话记忆。它的 transcript 随调用消亡——这正是隔离的落点。
- **子代理结构上无法递归**：受限目录不含 META 组，故 `spawn_agent` 在其中 `resolve` 不到（见 §3.10.4）。

#### 3.10.4 受限工具子集

三个焦点各有一套**由契约派生**而非手工维护的子集：

- **`review_tool_names()`**（焦点 `risk`）：`permission is READ and group in {FIN_DATA, GENERIC} and not needs_interactive and review_eligible`。当前结果：只读取数工具 + `read_file`/`read_pdf`。**不含** `web_search`。四类排除各有用意：
  - **`WRITE`**：子代理不得写入。
  - **META 组**：`research_plan`/`remember_preference` 有会话或全局副作用；`search_tools` 会让子代理自行扩大工具目录，`spawn_agent` 会让它递归派生。
  - **`needs_interactive`**：`ask_user` 在无交互通道的子 Agent 中无法工作。
  - **FIN_CALC 组**（额外排除）：`calc_metrics`/`calc_valuation` 只对调用方给定的输入做纯算术，不能独立取数。
  - **`review_eligible=False`**：联网工具。风险复核只核报告与会话自身数据，不得把不可信网页拉进这次阅读。
- **`general_tool_names()`**（焦点 `general`）：`review_tool_names()` + `web_search`。**不**把 `web_search.review_eligible` 改成 True，因此 risk 仍不得联网；general 仅在任务要求时联网。派发前若父闸门是 `PermissionGate` 且 EGRESS 未确认且非 AUTO，对 `web_search` 走一次与主循环同类的确认。
- **`reader_tool_names()`**（内部焦点 `reader`）：`permission is READ and group is GENERIC and ...`，即 **`{read_file, read_pdf}`**。**刻意不含取数工具**，理由见 §3.10.1.1。

`ToolRegistry(only=...)` **收窄目录本身**而非仅可见性：集合外的名字 `resolve` 不到，主 loop 以 "unknown tool" 拒绝。
受限目录内**没有任何按需工具**：按需激活是"让目录随运行增长"的机制，而受限目录是一份固定工作集，
在那里激活只会使子代理的能力边界随对话漂移。`only` 非空时 `_lazy` 直接为空集。
**三个子集都不含 META 组，因此子代理无法再派生子代理**，也无法请求任何方法论注入（`route_skills=False`）。

#### 3.10.5 失败隔离与闩锁

**报告本体永不受复核影响**（硬约束）。`BaseTool.run` 会把任何异常转成整个 `ok=False`，若复核异常穿出，一份渲染完好的报告会被丢弃。因此：

- 复核异常 → 降级为结果文本里的一行警告，报告仍 `ok=True`；
- 复核返回 `ok=False`（如 provider 报错、轮次耗尽）→ 同样降级；
- 侧车文件写失败 → 降级，意见已在结果文本中；
- 报告正文读取失败 → 降级为 `unreviewed`（2026-09 加固：此前 OSError 会穿出吞掉整份报告，与"报告本体永不受复核影响"自相矛盾）。

**降级必须读作"未经复核"**：报告正文刻意不改，所以工具返回值是调用方得知复核未发生的唯一途径。降级行的文案
明确标注「本报告未经独立复核，不得视为已复核交付」，而不是中性的"未完成"——后者容易被略过，等于静默放行一份
未复核的报告。系统提示词同步要求主 Agent 遇到该状态时如实说明，不得当作已复核。降级同时记成一条**未结事项**
（见 3.10.7）：未复核与"有未消解的高严重度问题"是同一类事实——复核所提供的保证缺失——因此走同一套机制；
只有"无复核者"的 `skipped` 例外，那是部署形态而非缺陷。

**闩锁按内容哈希**：`review.md` 头部记录被复核正文的 sha256。正文未变则复用既有意见（不重复付费）；正文已修订则重新复核。用 mtime 是错的——重写同一主题会覆盖报告文件，每次都会被判为"过期"。复用**不等于通过**：复用路径会把 sidecar 中的意见重新读出并重新解析严重度，因此正文没改时，其中未消解的高严重度问题照旧阻断。

#### 3.10.6 记账

`SessionStats` 增加 `per_agent` 维度（与 `per_tool` 对称）：

- 子 Agent 用自己的 `SessionStats` 跑，其工具统计**不**污染主 `per_tool`；
- 结束后 `add_usage` 把 token 计入主总量，`record_agent_usage(<focus>, ...)` 标注分项；总量与分项因此不重复计数。`per_agent` 按**任意 focus 字符串**键控，故 N 个 `general` 子代理累加 `runs`，无需改结构；
- `done` 事件暴露 `per_agent`，前端不改也能跑。

**成本叠加**：主 `usage` 始终是"含子 Agent 的总量"，M5 的 token 验收因此看得到全量成本。`spawn_agent` 一次派发 N 个任务即 N 份 token，故 `MAX_SPAWN_TASKS=8` 封顶，工具超时抬到 300（覆盖最慢的兄弟而非单次模型调用）。

#### 3.10.7 输出出口与可见性边界

复核意见**内联进 `write_report` 的 tool_result**（供主 Agent 在同一轮决策），同时落盘 `output/<topic>_<YYYYMMDD>.review.md`。不做前端复核面板——工作量与收益不成比例。终审是**模型对模型的内部质量闸门**：意见内容对用户不可见，用户侧也不应看到一份像"第二报告"的 sidecar。

三条边界（2026-09 收紧，起因是 sidecar 曾被当作产出文件列进"产出文件"供用户下载）：

- **sidecar 不入 `attachments`**，结果文本里也不给出它的路径。它保留在原路径，只承担两个职责：内容哈希闩锁、审计取证（3.7 的 `review` 行）。`GET /v1/artifacts` 的允许目录不加特判——用户看不到文件列表就无从构造 URL。
- **报告正文（md/docx）不写任何终审字样**。"已经独立复核"对用户是一句无从核验的保证，反而像背书；也会让文档渲染重新依赖复核结果，把刻意解耦的两件事绑回去。
- **状态可见、内容不可见**：终审是否发生、是否留有未消解问题，属于用户可直接询问的事实，模型应如实回答且使用系统给定的措辞；但复述意见正文、给出条目标题都不在这一档。

##### 严重度解析与未结事项

"这份报告是否还留着未处理的严重问题"必须是**系统持有的事实**，而不是留给模型去读懂的印象——否则模型可以在拿到意见后的任意一轮把它忘掉并照常交付。因此：

- `review.py:parse_findings()` 从意见里抽 `### [高|中|低] 标题` 条目；判定集中在 `ReviewOutcome.unresolved_note()`，工具结果的措辞与会话状态的注入都取这一处，不各自重新解释一遍。
- **只有高严重度构成未结事项**。中/低意见照旧附在结果里，但不阻断——否则闸门会被文风级意见淹没，反而更容易被整体忽略。
- **解析失败按未消解处理**。复核者的条目格式是提示词约定而非接口契约，抽不到任何条目时系统唯一诚实的表述是"不知道有没有严重问题"，故按存在严重问题处理（宁可多报一次，不可静默放行）。`未发现实质性问题` 用**整行精确匹配**，避免一句转述就伪造出一份干净的终审。空意见不在此列，沿用既有语义（未发现问题）。
- **未结事项挂在 `ResearchContext.review_findings`**（按报告主题键控），由 `state_block()` 注入每轮【会话研究状态】，措辞为"未消解的风险终审问题（须先修订，不得声称已复核）"。同一主题的**新终审结果整体替换**旧条目，使修订能真正清账；一个会话产出多份报告时各自独立记账。工具在 `metadata["review"]` 声明结局（审计钩子读同一份载荷，只取 `status`/`topic`/`review_path`/`error` 四个键，故审计行契约不变），循环在工具返回后写入 `ctx`。
- **有未消解高严重度项时**，tool_result 首行是阻断式措辞（列出条目、要求修订后重新成稿），且要求模型不得表述为"已完成/已复核"。`write_report` 不收 `path` 参数，修订必然重新经过权限闸门，因此修订动作对用户不是静默的。
- **未结事项只活在本执行窗口**（`ResearchContext` 随会话复用，TTL 见 3.12）。不落库：`notes` 是用户级、跨对话共享，会让一份报告的问题污染所有对话；`conclusions` 会被当作历史结论注入并出现在记忆视图里，等于把终审内容变成用户可见。跨重启的持久副本在 sidecar 与审计 JSONL 中已有，不需要第三份。

主 Agent 收到意见后自行决定是否用 `write_report` 修订；**子 Agent 不写报告**。
