### 3.10 coordinator/ —— 风险终审子 Agent（决策记录）

**职责**：在研报成稿后，用一个**独立的、受限的**子 Agent 复核报告的风险与数据支撑，输出修改意见供主 Agent 决定是否修订。

#### 3.10.1 设计决策记录

原设计（v1.1）规划了一个通用 `Coordinator.spawn_agent(task, focus)`，支持 `risk` 与 `macro` 两个焦点。**实际只落地 `risk`，通用接口未实现**，原因逐条记录如下：

| 原计划 | 决策 | 理由 |
|---|---|---|
| 通用 `spawn_agent(task, focus)` | **不做** | 只有一个调用方（风险终审）时，通用框架是纯粹的空壳；接口在出现第二个焦点时再抽象 |
| `macro` 焦点（宏观子 Agent） | **明确不做**（能力已具备，仍不实现） | 早先的理由"缺 `web_search` 工具"**已失效**——该工具与 `fetch_url` 已在 2026-09 落地（§3.4.1）。但**不实现 macro** 这个决定不变：宏观子 Agent 输出的是叙事型判断，无法像风险终审那样锚定到"核对报告数字是否与系统数据一致"的可验证产出，**独立性在这里换不来可检查的正确性**，反而多一个不受控的联网取数路径。若将来要做，应作为独立特性设计，不在本模块 |
| 并行取数作为子 Agent 价值 | **不成立**，已由 `asyncio.gather` 覆盖 | 主 Agent 已在同一轮内并行执行多个只读工具 |
| 上下文隔离 | **成立，且是唯一不可替代的价值** | 压缩（compaction）只是回收窗口空间，不提供独立视角 |

**因此**：子 Agent 只做一件事——**成稿后的风险终审**。它的价值来自"没有参与写作"且"能自己去核数据"，这是同一上下文里的自我检查拿不到的。

#### 3.10.2 触发点：为什么由 `write_report` 内部触发

复核由 `write_report` 工具**在渲染成功后自动调用**，而不是做成一个模型可选的只读工具。理由：

- **结构性保证**：把触发点放在报告工具内部，"每份报告都被复核"成为系统属性，而不是对模型行为的一个期望。若做成模型可选工具，模型完全可能写完就交付。
- **唯一入口即唯一场景**：只有研报生成会调用 `write_report`，因此"只在研报生成时复核"无需额外约束。

代价：`write_report` 与 coordinator 耦合；模型据意见修订重调 `write_report` 时会再次进入复核路径，故需要**内容哈希闩锁**（见 3.10.5）。

#### 3.10.3 隔离边界

```
主 AgentLoop
  └─ WriteReportTool._dispatch
       ├─ ReportPipeline.export()            ← 产出 md/docx
       └─ Coordinator.review_risk(topic, 报告正文（截掉附录）)
            ├─ 独立 ResearchContext + 独立 transcript + 独立 SessionStats
            ├─ 受限 ToolRegistry(only=review_tool_names())   ← 结构性隔离
            ├─ system = risk_review.md + risk-checklist 正文
            ├─ max_turns = 6（派生 settings，不动主 Agent 的 30）
            ├─ 共享 CitationRegistry                          ← cid 连续
            └─ 自己的 loop.usage → 回灌主 usage + per_agent["risk"]
```

- **共享 `cite`**：子 Agent 的取数自动续号（`cit_%06d`），"子 Agent 取的数据支撑了这份报告"因此进同一份溯源表。报告附录只收录 outline 中引用过的 cid，且附录在复核前已渲染完成，故复核的取数**不会污染已交付报告的附录**。
- **`store=None`**：复核是一次独立事件，不写对话记忆。它的 transcript 随调用消亡。

#### 3.10.4 受限工具子集

`review_tool_names()` 由**契约派生**而非手工维护白名单：`permission is READ and group in {FIN_DATA, GENERIC} and not needs_interactive`。

当前结果：8 个取数工具 + `read_file`。三类排除各有用意：

- **`WRITE`**：复核人不得写入。
- **META 组**：`research_plan`/`remember_preference` 有会话或全局副作用；`load_tool` 会让复核人自行扩大工具目录。`load_skill` 也排除——技能正文已由 system 注入。
- **`needs_interactive`**：`ask_user` 在无交互通道的子 Agent 中无法工作。
- **FIN_CALC 组**（额外排除）：`calc_metrics`/`calc_valuation` 只对调用方给定的输入做纯算术，不能独立取数，不增加核对能力。

`ToolRegistry(only=...)` **收窄目录本身**而非仅可见性：集合外的名字 `resolve` 不到，主 loop 以 "unknown tool" 拒绝。受限目录内无 lazy 工具——激活路径需要 `load_tool`，而受限目录没有它。

#### 3.10.5 失败隔离与闩锁

**报告本体永不受复核影响**（硬约束）。`BaseTool.run` 会把任何异常转成整个 `ok=False`，若复核异常穿出，一份渲染完好的报告会被丢弃。因此：

- 复核异常 → 降级为结果文本里的一行警告，报告仍 `ok=True`；
- 复核返回 `ok=False`（如 provider 报错、轮次耗尽）→ 同样降级；
- 侧车文件写失败 → 降级，意见已在结果文本中。

**降级必须读作"未经复核"**：报告正文刻意不改，所以工具返回值是调用方得知复核未发生的唯一途径。降级行的文案
明确标注「本报告未经独立复核，不得视为已复核交付」，而不是中性的"未完成"——后者容易被略过，等于静默放行一份
未复核的报告。系统提示词同步要求主 Agent 遇到该状态时如实说明，不得当作已复核。

**闩锁按内容哈希**：`review.md` 头部记录被复核正文的 sha256。正文未变则复用既有意见（不重复付费）；正文已修订则重新复核。用 mtime 是错的——重写同一主题会覆盖报告文件，每次都会被判为"过期"。

#### 3.10.6 记账

`SessionStats` 增加 `per_agent` 维度（与 `per_tool` 对称）：

- 子 Agent 用自己的 `SessionStats` 跑，其工具统计**不**污染主 `per_tool`；
- 结束后 `add_usage` 把 token 计入主总量，`record_agent_usage("risk", ...)` 标注分项；总量与分项因此不重复计数；
- `done` 事件暴露 `per_agent`，前端不改也能跑。

**成本叠加**：主 `usage` 始终是"含子 Agent 的总量"，M5 的 token 验收因此看得到全量成本。

#### 3.10.7 输出出口

复核意见**内联进 `write_report` 的 tool_result**（供主 Agent 在同一轮决策），同时落盘 `output/<topic>_<YYYYMMDD>.review.md` 作为可审计证据。不做前端复核面板——工作量与收益不成比例。

主 Agent 收到意见后自行决定是否用 `write_report` 修订；**子 Agent 不写报告**。
