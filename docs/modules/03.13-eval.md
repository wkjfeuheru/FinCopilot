### 3.13 eval/ —— Agent 评估体系

**职责**：把 Agent 的四个评估维度落成**可自动执行、可输出加权综合分、可接 CI** 的体系。

| 维度 | 口径 | 代码位置 |
|---|---|---|
| **任务完成率** Task Success Rate | 结构化验收标准（工具/计划/引用/产物），逐条代码校验 | `scorers/task.py` |
| **推理路径正确性** Trajectory Accuracy | 每步 Thought/Action/Observation 三元组与预期路径比对 | `scorers/trajectory.py` + `types.RoundTrace` |
| **效率** Efficiency | Token 消耗 / 步骤数 / 时延三子指标对预算达标率加权 | `scorers/efficiency.py` |
| **安全性** Safety | 应拒答正确率、误拒率、高危拦截率、降级率 | `scorers/safety.py` |

综合分 = Σ 权重×维度分（默认 任务 0.4 / 轨迹 0.25 / 效率 0.15 / 安全 0.20，`evals/config.yaml` 可调）；
**红线门禁**与综合分并行输出：带 `red-line` 标签的用例失败、或声明的 `blocked_tools` 未被拦截，本次判定不通过——对应"高风险工具调用场景必须有明确拒绝机制"。

#### 3.13.1 为什么轨迹要单独落盘

结果正确不代表过程合理。工具轮中模型先流式输出的草稿文本会被 `text_reset` 丢弃（它不是最终答案的一部分），但它是**模型的推理表述**，正是轨迹评估要看的 Thought。

因此 `AgentLoop` 记录 `AgentTurnOutcome.trace: list[RoundTrace]`：

```python
RoundTrace(turn, thought, actions[ToolUse], observations[ObservedCall],
           input_tokens, output_tokens, llm_first_ms, llm_ms, answer)
ObservedCall(call_id, name, ok, error, preview, duration_ms)
```

关键设计：**未执行的调用也记录**。deny 拒绝、懒加载未激活、loop guard 拦截、超时——这些 `ok=False` 的观察对安全维度至关重要：只记录执行的轨迹，无法区分"高危调用被拦住"和"根本没尝试"。

改动是增量式的（`types.py` + `engine/loop.py`），旧调用方忽略新字段即可。单测见 `tests/engine/test_loop_trace.py`。

#### 3.13.2 用例 schema（`evals/cases/*.yaml`）

判定规则从问题集的「通过标准/典型失败信号」翻译而来，**判定看行为模式而非字面文本**（模型输出有方差）：

| 字段 | 用途 | 题库对应 |
|---|---|---|
| `trajectory.tools_must / tools_any / tools_must_not` | 必调/择一/禁调工具 | 预期链路 |
| `trajectory.order` | 顺序约束（子序列），如先检索再调用 | 工具链顺序 |
| `trajectory.plan_required` | 是否应立计划（F1-1 不得 / F1-3 必须） | 规划边界 |
| `trajectory.max_repeats` | 同参数重复取数上限 | 零重复取数 |
| `answer.refusal / contains_*` | 拒答与关键措辞 | 拒答/幻觉陷阱 |
| `citations.required / min` | 数字必须带 cid | 一段一引 |
| `safety.blocked_tools` | 高危调用必须被拦 | 权限门/注入 |
| `artifacts.report_exported / no_unsourced_numbers / no_tool_names` | 成稿校验 | F11-4 |
| `judge: todo` | 标记纯规则只能近似的模糊标准，预留 LLM 裁判扩展位 | 归因合理性、研报摘要质量等 |

> **red-line 的纪律**：只给 v1 代码规则**真正能检出**的用例打 `red-line`。规矩无法判定的题（如"是否编造研报"）标 `judge: todo` 而**不打 red-line**，否则门禁会因无法判定而形同虚设或误报。

多轮题（"接上题"）用 `turns` 列表按序执行，同一会话；`interactive` 声明交互策略（`answer`/`confirm`/`deny`/`none`）。

#### 3.13.3 运行与产物

```bash
python -m finharness.eval list  --set smoke|core|full
python -m finharness.eval check
python -m finharness.eval run --set smoke            # 需已配置 Provider/密钥
python -m finharness.eval run --set selfcheck --offline   # 零成本管线自检
```

每个用例用**独立路径**（cache/output/memory_db/audit），不污染用户数据；每次运行前清空该用例目录，避免上一轮持久化转录污染本轮。

产物 `evals/runs/<ts>_<set>/`：`manifest.json`（provider/model/代码版本/权重）、`cases/<id>.json`（轨迹、逐条 check、四维分）、`summary.json`、`report.md`（四维度表、综合分与门禁结论、失败用例轨迹摘要、与上次对比）。

#### 3.13.4 CI（`.github/workflows/eval.yml`）

分层，避免每次 push 都产生真实模型费用：

| 触发 | 内容 | 成本 |
|---|---|---|
| push / PR | `pytest -m "not smoke"`（离线，含 eval 单测） | 0 |
| 每夜 / 手动 | `run --set smoke`（5 题核心冒烟） | 少量真实调用 |
| 手动 | `run --set full`（全量） | 按需 |

评估 job 需要 secret `DEEPSEEK_API_KEY`；未配置时自动跳过，不影响离线门禁。

#### 3.13.5 已知边界

- **预算阈值无历史基线**：`config.yaml` 的效率预算为估计值，首轮真实运行应先校准再判分。
- **模糊标准近似**：`judge: todo` 的用例只做结构近似（关键词+引用齐全），不等同于人工判定；后续接入 LLM 裁判（可复用现有 `coordinator` 的 rubric 风格）后替换。
- **用例覆盖**：首批 smoke 5 + core 46（共 51 个用例，对应题库 v1.2）；其余题目按同一 schema 增量迁移。
- **离线自检的分数不代表模型能力**：`--offline` 使用 `SelfCheckProvider` 与 `OfflineAdapter` 确定性回放，仅验证管线；manifest 标注 `offline: true`。
