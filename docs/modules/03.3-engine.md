### 3.3 engine/ —— Agent Loop 核心

**职责**：驱动模型-工具闭环；承载治理、并行、超时、裁剪、成本；对上层只暴露 `AgentLoop` 一个门面。

**3.3.1 AgentLoop 状态与构造**

```python
class AgentLoop:
    # 组装自 cli.main()/server api；依赖全部注入，便于单测注入 FakeProvider
    def __init__(self, *, provider: Provider, registry: ToolRegistry,
                 gate: PermissionGate, hooks: HookChain, ctx: ResearchContext,
                 settings: Settings, cite: CitationRegistry,
                 output: OutputSink): ...   # 输出端：rich(CLI)/SSE(HTTP) 实现 emit
    async def run(self, user_msg: str) -> AgentTurnOutcome: ...
```

**3.3.2 主循环算法（turn 级）**

```text
run(user_msg)
 1 ctx.append_user(user_msg)
 2 while turn < ctx.max_turns:
 3    request = ContextAssembler.build(ctx)         # system + 历史 + 活跃工具schema(§3.4.3)
 4    events = provider.stream(request)              # 含 retry(§3.3.4)
 5    增量聚合：text_delta → 立即 output.emit(text_delta)（逐字流式，不等整段生成完）
      tool_use_delta → 累积；终答/结论/确认 → emit 对应 EngineEvent
 6    if events 以 MESSAGE_END 结束 且 无 tool_use:
 7        append assistant 终答 → 返回 outcome(答案全文, usage累加)
 8    if 有 tool_use:
 9        若本轮已流出草稿 → emit text_reset（客户端丢弃草稿）
10        append assistant(仅工具调用帧)到 ctx（正文草稿不入上下文）
11        results = await asyncio.gather(*[ self._execute_one(tc) for tc in tool_uses ])
12        for r in results: ctx.append_tool_result(r)      # 裁剪已在 _execute_one 内完成
13        emit plan_progress（见 §3.3.9），并把目标漂移/停滞软提示挂到下一轮状态块
14        continue
15 若超 max_turns 仍无终答 → outcome.succeeded=False, reason="max_turns_exhausted"
   （**仍以 answer 回传部分成果**，并落盘；见 §3.3.6）
```

> **失败收尾不空手**：`loop_detected`、`max_turns_exhausted`、`provider_error` 三条失败路径都会
> 调 `_partial_answer(reason)` 汇总已形成的结论与已取数据，经 `answer` 事件下发，并作为一条 assistant
> 消息落入转录（随 `_persist_turn` 持久化），因此重开对话仍可恢复。`_fail` 只在有内容时才发
> `answer` 事件；`provider_error` 仅当已有结论或引用时才附带部分成果。

> **流式与草稿回滚**：`text_delta` 在到达时即下发，回答因而逐字出现；但模型在「决定调工具」前写的正文属于草稿，
> 一旦本轮出现 `tool_use`，先发 `text_reset` 让客户端清空已显示的草稿，再执行工具。最终答案在后续轮次重新流式输出，
> 且 `answer`/`done` 的收尾顺序不变。重试只在首个 chunk 之前发生（§3.3.4），因此逐字下发不会产生重复文本。

**3.3.3 `_execute_one(tc)` —— 治理执行链（串行单工具）**

> 实现进度：①②③⑤⑥ 均已落地（`PermissionGate` + `HookChain` + `tool.render`）；`run_python` 暂不发布（§3.7.2），故沙箱分支无对应工具。超时取值为「`settings.tools.timeout_overrides` → 工具声明的 `timeout` → `timeout_default_s`」三级回退。

```text
_execute_one(tool_use)
 ① tool = registry.resolve(tool_use.name)
 ② verdict = gate.check(tool)                     # 权限判定（§3.7.1）
    - DENY          → 生成结构化错误 ToolResult(error=解释)
    - NEED_CONFIRM  → cli 渲染确认（非交互模式=auto）→ 用户 n → 取消结果回填
 ③ hooks.pre(tool, args)                          # 可中断（返回 False→阻断）
 ④ raw = await execute_with_timeout(tool, args)   # asyncio.wait_for，超时→ToolResult(error)
    - execute 内部走 cache → adapter（降级）→ RawData
 ⑤ payload, citations = tool.render(raw)          # 工具自渲染裁剪文本 + 注册溯源
    - 若工具缺 render → 默认 DataFrame → markdown 裁剪（§3.6.1）
 ⑥ hooks.post(tool, args, outcome, citations)     # 审计落盘（§3.7.3），异常不影响结果
 ⑦ return ToolResult(content=payload, ok, citations, error)
```

**3.3.4 重试（retry.py）**：作用于 Provider 请求层。
- 触发条件：429 / 5xx / 连接重置 / 首字节超时。
- 指数退避：`delay = min(cap, base * 2**attempt) + jitter(0, base)`，base=1s，cap=30s；最多 4 次。
- 429 附带 `Retry-After` 时以该值叠加；每次重试计入 `SessionStats.retry_count`。

**3.3.5 用量与会话统计（cost.py）**：每轮 `provider.stream` 结束后累计 `ModelUsage.input/output_tokens`，并统计重试次数、工具请求数与分工具耗时（`SessionStats`）。`done` 事件与 `AgentTurnOutcome` 输出这些计数；金额折算不在当前范围内。

**3.3.6 工具结果预算（`shared/budget.py`）**：单条结果的 token 预算由 `resolve_result_budget` **单点解析**，
优先级与 `timeout` 对称——运维覆盖 `tools.result_token_overrides[name]` > 工具声明的 `BaseTool.result_tokens`
> 全局 `context.max_result_tokens`，`detail="full"` 的放大（`FULL_DETAIL_MULTIPLIER`）**只在该处应用一次**。

两处消费者读同一个数字：工具渲染时（`tools/base.py:_result_token_budget`）与引擎编码时
（`engine/loop.py:_result_budget` → `_truncate`）。这一点是必需的，而非整齐而已：过去两侧各自读取全局设置，
渲染侧对 `detail="full"` 乘了 4 倍而引擎侧没有，于是放宽渲染出的内容又被砍回原预算——"再多给点"这个逃生口
有一半是失效的。不同工具的合理结果体量相差极大（一次报价 vs 一份研报全文的句柄清单），因此预算必须可按工具声明。

截断标记是**可据以行动**的：`[truncated]已省略约 N/M token；完整内容见 <路径>（可用 read_file / read_pdf 分页读取）`。
路径取自工具自报的落盘位置（`RawData.parquet_path` / `paths`）。仅写 `[truncated]` 曾使"只看到研报首页"无法被诊断——
读者既不知道丢了多少，也不知道去哪里取回。

**3.3.7 关键不变量（写进单测）**
1. 每个 tool_use 必有一个配对的 tool_result 回填（`call_id` 一一对应，缺失即会话失败）。
2. 裁剪后单条 tool_result.content 长度 ≤ 该工具解析出的结果预算（默认 `context.max_result_tokens`），
   且 `detail="full"` 的渲染结果**不得**被引擎砍回 1× 预算。
3. 任意工具异常不得击穿 Loop：一律转 `ok=False` 的结构化文本让模型决策。
4. `write_report`/`write_file` 未确认前不得触发 hook.post 的"成功"审计（记录为 pending/denied）。
5. **循环兜底**：同一 `(工具名, 规范化参数)` 在同一 run 内重复达 `context.max_identical_tool_calls`
   （默认 3）即被拒绝执行（结果已在上下文与缓存中，重复调用无信息增量）；**该调用再次出现则终止本轮**。
   终止时 `reason="loop_detected"`，且必须以 `answer` 回传**已有成果**（结论与引用），不允许空手失败。
6. **失败收尾不空手**：所有不成功的终态（`loop_detected` / `max_turns_exhausted` / `provider_error`）
   都经 `_partial_answer(reason)` 回传已有结论与引用，并作为 assistant 消息落盘（重开对话可恢复）；
   仅当确实无成果时 `answer` 才为空。
7. **per-run 状态**：`turn`、重复计数、计划签名/停滞计数均在 `run()` 入口重置（轮次预算按请求计，
   非按会话累计）。
8. **计划软约束**：计划进度/目标漂移只产生 `plan_progress` 事件与状态块软提示，**从不拒绝调用**；
   复杂度判断的唯一真源仍是 `ctx.plan is not None`。
9. **中断必留成果**：`CancelledError` 继承自 `BaseException`，会穿出 `_run_turns` 里所有
   `except Exception`；`_run_once` 因此用 `try/except BaseException` 兜住它，**先**同步调用
   `_persist_turn()` 与 `_save_checkpoint("stopped", "interrupted")` **再**重新抛出。
   没有这条，用户提问与本轮全部中间成果会随取消静默消失。
10. **停止不是失败**：`_stop_turn` **不发** `error` 事件，只发 `answer`（部分发现）+
    `done(reason="user_stopped", resumable=True)`；工具调用被中断时沿用 `_aborted_results`
    补齐配对，保证下一轮请求格式合法（不变量 1）。

**3.3.11 用户主动停止与断点恢复（v1.2 新增）**

- **信号**：`StopSignal`（`finharness/types.py`，`asyncio.Event` + reason）挂在 `AgentLoop.stop_signal`
  上，默认 `None`，因此 eval、脚本与子代理等不经服务层的调用方行为完全不变——没有信号就永不检查。
  服务层创建并置位它（§3.12.8），引擎只读 `_stopped()`，无需 await 也无需轮询。
- **检查点位置**：① 每个流式 chunk（覆盖最常见场景：用户看着长回答在流式输出时按停止）；
  ② 每轮边界（此时一轮已完整收尾，停下不会破坏记录格式）；③ 工具 `gather` 返回之后——**这条最关键**，
  用户在耗时调用期间按下的停止会保住这次调用已取得的成果，而不是连它一起丢弃。
- **收尾**（`_stop_turn`）：仿 `_fail` 但走"停止"语义——汇总 `_partial_answer(reason="user_stopped")`
  交付并 append 为 assistant 消息（随本轮落库）；无成果时发 `text_reset` 清掉流式中途的半句话，
  避免用户把截断的草稿误读成答案。
- **断点**：`_save_checkpoint(status, reason, partial_answer)` 覆盖写 `turn_checkpoints`（§3.6.9）。
  每轮收尾按结论记为 `completed`/`stopped`；硬取消路径记为 `stopped/interrupted`。
  写入是**同步 SQLite**——这正是它能在被取消的任务里跑完的原因。
- **恢复**：`_load_memory_if_first_turn` 之后调 `_restore_checkpoint()`：若最新断点可继续
  （`status=stopped`）且带计划，则 `Plan.from_dict` 装回 `ctx.plan`，并**消费掉断点**
  （清空它，避免运行途中界面仍显示"可继续"；本轮收尾会写入属于它自己的新断点）。
  计划是唯一无法从消息重建的执行态（只活在 `ctx` 里），因此它就是恢复的全部内容；
  `plan_id`/`revision` 原样还原，使后续修订与进度台账不失真。`completed` 断点不参与恢复。
- **子代理**：`Coordinator` 通过 `stop_signal_provider` 取值器把主循环的信号传给每个子 `AgentLoop`
  （取值器而非快照，因为信号在 loop 构造之后才装上），因此报告终审/并行研究期间按停止同样生效。

**3.3.7 系统提示词（prompts/system.md）**

- 单点定义：`engine/prompt.py` 从 `src/finharness/prompts/system.md` 读取，`server/api.py` 与全部 e2e 测试
  引用同一份文本——**提示词本身是被测对象**，不得在测试里另写一套（否则产品行为从未被验证）。
- 提示词共 7 节：**角色与能力边界**（具体身份 + 能做/不能做 + 知识边界：
  模型记忆不得充当数据 + **做不到时的处理**：缺输入→`ask_user`、超边界→说明并给替代、
  取不到→说明缺什么，底线是不得猜测/编造、"取不到"优于"看似完整的错答案"）、
  **何时规划**（判据是"是否需要串联多个阶段"，而非工具调用数量）、
  **取数与收敛**（不重复取数/复用 citation 与收敛是同一条纪律：**合并为一节**；
  含懒加载联网工具的用法）、
  **引用与溯源规范**（`{cite:cid}` 占位符 + **正/反示例**、一段一引、不得虚构引用、无来源数字会被标记）、
  **工具与技能的调用边界**（默认在对话内作答；成稿与配图按需——"成稿只在明确要求时"与
  "配图只在需要时"**合并为一条**，不得把分析自行升级为成稿；含 `write_report` 入参 JSON 示例）、
  **记忆与状态**（历史结论可复用、时效校验、跨对话偏好）、
  **输出纪律**（不做买卖建议、口径差异说明、面向读者不复述内部过程）。
- **拒绝策略并入角色节**（而非独立成节）：做不到是能力边界的后果，二者是一件事；测试断言该策略
  在角色节内、且不再出现独立标题，防止将来又漂移出去。
- **去重原则**（2026-09 精简）：同一约束只在一处声明，其余处引用。已消除的重复——
  "数字只来自本次取数"由 4 处并为 1 处（知识边界），"不重复取数"由 4 处并为 1 处（取数与收敛），
  "投资建议"由 2 处并为 1 处（不能做；输出纪律改为指回）。合并后 8 节 → 7 节，
  4272/3496 → 3490/2888 token（-17%）。
- **格式约束一律"描述 + 示例"**（2026-09 设计补充）：仅靠描述不足以稳定参数解析。两处示例各自锚定其规则——
  引用占位符（正文专有约定、无 JSON Schema 兜底）给正/反例；`write_report`（唯一嵌套结构）
  给骨架示例，且**该示例由测试对真实 `ReportInput` 校验**，防止示例与 schema 漂移。
  扁平且已有 schema 每轮注入的工具（如 `research_plan`）不再重复给示例，以省常驻 token。
- 提示词每轮请求重发，改动需计入常驻成本：本次设计补充使其由 2869 字符 / 2379 token
  增至 3490 字符 / 2888 token（+21%）。
- "是否复杂"只有一个真源：模型是否调用了 `research_plan`（即 `ctx.plan` 是否存在）。
  提示词不逐字判断复杂度，代码也不做分类——避免代码与模型两套判断打架。

**3.3.8 前缀缓存友好布局（2026-09）**

- **约束**：System Prompt 与请求前缀在**每次请求中必须逐字相同**，缓存才能命中；任何动态内容
  （当前日期、用户信息、会话状态）都必须放进消息，不能进 system。Provider 侧缓存顺序是
  `tools → system → messages`，任何一环变化都会使其后失效。
- **原问题**：`_system_prompt()` 曾返回 `self.system + ctx.state_block()`——状态块含计划/结论/
  召回/摘要/偏好，**agent 循环内每次迭代都可能变**。它在消息之前，于是缓存前缀止于静态文本，
  **整段历史每轮按全价重算**。
- **现布局**：`_system_prompt()` 只返回静态 `self.system`；状态块改为**请求末尾的临时 user 消息**
  （`_request_messages()`，不落盘、不进转录、不参与摘要）。请求 = `[静态 system] + 历史 + [状态消息]`。
  每次迭代的共同前缀即上一轮全部内容，只有新增的 tool_result 被处理。
- **窗口测量同步**：`request_tokens(..., extra_text=状态)`；`AutoCompactor` 透传 `state_text`。
  否则压缩会低估窗口、放行超额请求。
- **可观测**：`ModelUsage` 增 `cache_hit_tokens`/`cache_miss_tokens`；OpenAI 路径解析
  `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`，Anthropic 路径解析
  `cache_read_input_tokens`/`cache_creation_input_tokens`；`SessionStats` 聚合，`done` 事件
  暴露 `cache_hit_tokens`/`cache_miss_tokens`/`cache_hit_ratio`。
- **实测**（`scripts/measure_prefix_cache.py`，同一问题、同一数据源、DeepSeek 自动前缀缓存，
  两次独立运行结果一致）：

  | 配置 | 命中率 | 全价（未命中）token |
  |---|---|---|
  | 状态在 system（旧） | 30~31% | 25344~25532 |
  | 状态在请求末尾（新） | **78%** | **7366~8298** |

  **命中率 30%→78%，全价 token 降约 67%**。DeepSeek 缓存命中价约为未命中的 1/10，故实际输入
  费用降幅大于 token 降幅。
- **已知限制（未做）**：Anthropic 兼容链路（Kimi/GLM）需要显式 `cache_control` 断点才启用缓存，
  本实现未发断点，故其缓存收益尚不可得。**且状态改为末尾 user 消息后，若上一条历史已是
  tool_result（其角色的 user），会出现两个连续 user 消息，Anthropic 会拒绝**——使用 Kimi/GLM
  前需先合并这两条。DeepSeek/OpenAI 兼容链路不受影响。
- **未做**：工具集合在会话内仍可能因按需激活而变化（`tools` 属缓存前缀）。激活已不再稀有——检索与
  直接调用都会触发——因此长会话里的常驻集合会单调增长。缓解是 `tools.max_active`（默认 0 = 不限）：
  超限时按最久未用把按需工具退回未激活态。仍不做常驻全量 schema（那会牺牲每轮常驻 token）。

**3.3.10 场景路由（2026-09）**

- **注入点**：`_route_methodology` 在 `_run_once` 里、轮次循环之前调用一次。放在这个位置有两个后果——
  第一次模型调用就已经看得到方法（不必等到某一轮才补上）；**没有计划的简单提问也能拿到方法论**，
  因为它不依赖任何模型发起的调用。
- **输入**：用户消息与计划意图推断出的能力集合（`capabilities_in_text`）+ 计划步骤的 `skill_hint` +
  是否明确要求成稿。**输出**：要注入的目标列表，正文写进 `ctx.methodology`，由状态块按轮渲染。
- **幂等**：同一目标每会话只注入一次；只有首次注入才发射 `context_routed`（携 `skills` 与 `capabilities`），
  使隐式加载可归因，也供重放与 eval 读取（`CaseRun.loaded_skills()`）。
- **不阻断**：技能包缺失或格式错误只是"这份方法这次没有"，跳过并继续，绝不让一次回合失败。

**3.3.9 计划进度与偏离可观测（2026-09）**

- **背景**：`ctx.plan` 曾是纯文档——`mark_plan_step`/`add_conclusion`/`PlanStep.dep` 无生产调用者，
  步骤状态永远是 `○ pending`，唯一自动护栏是字面重复计数（抓不到语义跑偏）。现将其变为**可回写、
  可观测**的工作账本，但仍是**软约束**：只回写状态、渲染进度、注入提示，**不阻断任何工具调用**。
- **回写**：新增 META 工具 `update_plan_step`（写步骤 `done/fail/skipped/pending`）与
  `record_conclusion`（落结论及其 citations），两者 READ 权限、常驻，直接改 `ctx`。系统提示词要求
  每完成/放弃一步就回写、形成结论就记录，否则进度失真。
- **渲染**：`plan_digest()` 首行给出 `进度 done/total`，每步渲染其依赖的当前状态
  （`依赖：1✓,2○`），使未满足的前置条件一眼可见。
- **目标漂移/能力错配/停滞检测（`_plan_progress`，每轮工具执行后）**：
  - **目标漂移** `drift`：本轮工具调用的 `symbol` 不在计划声明的标的集合内（计划的目标/步骤/工具提示里出现的
    6 位代码即声明标的）。**判定的是目标而非工具**：取数、读缓存、查公告、画图都只是完成任务的手段，
    用哪个工具都不算偏离；只有把分析对象扩到了任务未点名的标的才算真正偏离。**仅当计划声明了标的才判定**
    （行业/宏观题不点名标的，则不判漂移）；同一标的只报一次，避免每轮重复提示。
  - **能力错配** `mismatch`：本轮调用工具所属的**能力**（见 `shared/capabilities.py`）不在计划各步
    `tool_hint` 映射出的期望能力集合内。**判定在能力层而非工具层**——`get_quote`/`get_kline` 同属"行情"、
    `detail=full`、`with_text=`、`method=` 等策略与模式差异都不算错配；只有用错了**能力**（如查公告却用了新闻）
    才报。仅 META/输出/文件/联网以外的**研究类能力**参与判定；同样仅当计划声明了 hints 才判、同一能力只报一次。
  - **停滞** `stalled_turns`：计划签名 `(revision, 各步骤状态)` 连续多轮不变；达
    `context.plan_stall_turns`（默认 2）即触发。
  - 三者经 `plan_progress` 事件透出（`{revision, done, total, stalled_turns, drift, mismatch}`），并把软性
    提示追加到**下一轮**状态块的末尾（`_state_text`），提示模型核对目标、换回正确能力或回写进度。
  - **边界**：能力判定抓**能力替换**（公告 vs 新闻、宏观 vs 行业）；抓不到**同能力的参数/模式误用**
    （`get_market_news` 用 symbol 还是 topic、`run_backtest` 单股 vs 横截面、`get_kline` period）——
    那属参数纪律，由工具描述与专项测试覆盖。
- **按需激活（原"懒加载门禁"）**：调用未激活的按需工具时，`_execute_one` **就地激活并继续执行**，
  不再结构化拒绝。按需注入是省 token 的手段而非权限：模型一旦点名调用某个工具，就说明它已经知道
  要什么，此时拒绝只会白费一轮。激活同时写入 `ctx.loaded_tools`，并发射 `tool_activated` 事件
  （span 上记 `lazy_activated` 属性，不覆盖本次调用自身的终态）。
- **可见性**：`done` 事件新增 `plan` 字段（`{revision, done, total}`），使重规划（revision 递增）
  与计划完成度对上层可观测。
- **成本取舍**：两个 META 工具常驻，`tools` 前缀新增 2 个 schema，会使前缀缓存失效一次；
  按"计划可回写"的收益接受。
