# 03.13 认证与多用户隔离

## 1. 职责

为 Web 层提供用户注册、登录与会话管理，并把所有持久化数据
约束到当前用户的作用域内。设计目标有两条：

* **认证**：除存活探针与认证端点外的所有 `/v1` 端点都要求身份；
* **隔离**：任何用户数据都不能被另一个用户读取或改写，
  包括对话、消息、引用、结论、偏好、供应商配置与产物文件。

CLI 与 eval 直连场景不起 HTTP 层，其 `user_id` 为空串，
行为与引入认证之前一致。

## 2. 凭据模型

### 口令

`auth/passwords.py` 使用 PBKDF2-HMAC-SHA256，哈希串自描述：

```
pbkdf2_sha256$<iterations>$<salt_hex>$<hash_hex>
```

迭代数随串存储，因此日后提升参数不会让既有口令失效。
比较用 `hmac.compare_digest`，恒时。明文口令绝不落盘、绝不回显。

### 会话令牌

登录/注册成功后签发不透明令牌 `t_` + 32 字节随机十六进制。
**令牌本体只下发给客户端一次**，库中只存其 SHA-256
（`auth_sessions.token_hash`）。因此数据库文件泄露也无法冒充登录。

令牌带 TTL（默认 14 天，`auth.token_ttl_s`），可撤销
（`POST /v1/auth/logout`），过期行在每次签发时顺带清理。

### 传输通道

同一令牌支持两条通道，解析顺序为 Cookie 优先：

| 通道 | 用途 |
|---|---|
| `finharness_session` Cookie（HttpOnly + SameSite=Lax） | 同源浏览器，无需任何请求头改造 |
| `Authorization: Bearer <token>` | 脚本、测试与跨源调用方 |

前端与后端同源部署（Vite 代理 / FastAPI 静态挂载），
因此 Cookie 方案不需要 CORS 配置。经 HTTPS 对外暴露的部署
应设 `auth.secure_cookie=true`，使 Cookie 只走加密信道。

## 3. 端点

| 方法 + 路径 | 说明 |
|---|---|
| `POST /v1/auth/register` | 注册并立即签发会话；重名 409，弱口令/非法用户名 422 |
| `POST /v1/auth/login` | 校验凭据并签发新令牌；失败统一 401 |
| `POST /v1/auth/logout` | 撤销当前令牌并清除 Cookie |
| `GET /v1/auth/me` | 当前用户身份；未登录 401 |

`/v1/health` 与 `/metrics` 保持开放——编排器需要能探测容器。

### 不在任何响应中的内容

* 口令明文与哈希；
* 令牌哈希；
* 其他用户是否存在（跨用户访问一律 404，而非 403）。

登录失败时，用户不存在与口令错误返回**同一条消息**，
且都对口令做一次哈希计算，使两种路径在时间上不可区分，
避免用户名枚举。

## 4. 隔离约束

### 4.1 存储布局（共享库 + `user_id` 列）

按 `docs/03.13` 的决策，所有用户共用一个 `memory.db` 与一个
`config.db`，隔离靠列过滤实现：

| 表 | 隔离方式 |
|---|---|
| `conversations` | 加 `user_id` 列，索引 `(user_id, last_active_at)` |
| `notes` | 主键改为 `(user_id, key)` |
| `provider_configs` | 加 `user_id` 列；名称唯一与“单一激活”索引都按用户 |
| `messages` / `summary_segments` / `citations` / `conclusions` / `conversation_symbols` | 经 `conversation_id` 传递隔离，结构不变 |

产物文件按 `output/<user_id>/` 物理分目录：每个用户在 `loop_factory`
中获得一份 `output_dir` 指向该子目录的 settings 视图，工具层
（`chart`、`report_pipeline`、`write_file`）无需改动即写入正确位置。

### 4.2 句柄必须校验归属

`session_id`、`conversation_id`、`config_id`、`request_id` 都是
全局唯一句柄，因此**任何按句柄的访问都必须同时校验归属**：

* `SessionRegistry.ensure` 命中 `session_id` 时校验 `session.user_id`；
* `ConfirmBus.respond` 校验挂起请求的归属，B 不能替 A 批准写操作；
* `ConfigStore` 的每个按 id 方法都带 `user_id` 过滤，否则 A 可以
  激活或删除 B 的配置；
* 对话与引用端点先查归属再返回值。

归属不符按“不存在”处理（404）。会话正忙与“会话属于他人”
返回同一条消息（409），不泄露归属信息。

### 4.3 保留策略按用户

`MemoryStore.prune` 按用户分别计算预算：每个用户独立享有
`retention_conversations`（200）与 `retention_days`（180），
一个重度用户不会挤掉另一个用户的对话。

### 4.4 下载范围

`/v1/artifacts` 的允许根为：

* `output/<当前用户>/`
* `data_cache/parquet/`

`tools/generic/files.py` 的 `read_file` / `write_file` 同步收窄到
`data_cache/parquet/` 子树。收紧的必要性：此前整个 `data_cache/`
可下载，意味着 `users.db`（口令哈希）、`memory.db`（全用户对话）
都能经该端点被拿走。

### 4.5 不留跨用户痕迹

`AuditHook` 的 `session_start` / `session_end` 行记录 `user_id`，
使审计日志可按用户归属检索。

## 5. 存量数据迁移

两个存储的 `__init__` 都用 `PRAGMA table_info` 检测列存在性后
原地升级（`notes` 与 `provider_configs` 因需改主键/唯一约束，
走建新表-拷贝-替换）。存量行的 `user_id` 为空串。

**第一个注册的账号继承全部存量数据**：`UserStore.register` 在
users 表原本为空时调用 `claim_legacy`，把 `user_id=''` 的对话、
笔记与供应商配置划归该用户。因此单用户安装升级后数据不丢。

## 6. 配置

```json
"auth": {
  "token_ttl_s": 1209600,
  "min_password_len": 8,
  "secure_cookie": false,
  "allow_register": true
},
"paths": {
  "auth_db": "data_cache/users.db"
}
```

用户名规则：2–32 个字符，仅限字母、数字、下划线、连字符或中文，
大小写不敏感地唯一。口令最短 8 个字符（`min_password_len` 可提高）。

`allow_register=false` 可关闭自助注册（用于只允许既有账号的部署）。

对应环境变量：`FINH_AUTH_TOKEN_TTL_S`、`FINH_AUTH_MIN_PASSWORD_LEN`、
`FINH_AUTH_SECURE_COOKIE`、`FINH_AUTH_ALLOW_REGISTER`、`FINH_PATHS_AUTH_DB`。

## 7. 前端

`LoginScreen` 在未登录时整页替换工作区，登录/注册共用一块表单。
`App.tsx` 挂载时先 `GET /v1/auth/me` 探测会话；任何 API 返回 401
时 `api/http.ts` 派发全局事件，应用回到登录页。

本地记住的对话句柄按用户分键
（`finharness.conversation_id.<user_id>`），换账号登录不会
串到另一个用户上次打开的对话。

## 8. 验收

* `tests/server/test_auth.py`：注册、登录、登出、双通道、
  口令与令牌的存储形态、访问控制；
* `tests/server/test_isolation.py`：两个用户 A/B 之间的
  对话/消息/引用/结论/偏好/配置/产物/交互确认全部不可互通；
* 全量回归 `uv run pytest`。
