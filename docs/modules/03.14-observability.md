### 3.14 observability/ —— 可观测性层

三层各自独立、各自可降级：**结构化日志（JSON）、Prometheus 指标、LangSmith 追踪**。调用方只依赖 `Observer` 门面，因此是否接后端、装了哪些依赖，对引擎与测试都透明。

**3.14.0 三条不变量**

1. **尽力而为**。与 `HookChain.post` 同一原则：观测绝不破坏一次回合。每个后端调用都包在 `try/except` 中，失败只降级并留一条 debug 日志。
2. **后端缺席即 no-op**。`prometheus_client`/`langsmith` 是可选 extra；未安装或未启用时 `build_observer` 返回 `NullObserver`，行为与引入观测之前逐字节一致。
3. **凭据绝不落盘**。`redact` 是唯一脱敏入口（审计 hook 也复用它）；完整 Prompt/响应默认**不记录**，显式打开 `capture_payloads` 后仍先脱敏再截断。

**3.14.1 结构化日志（logs.py + context.py + redact.py）**

- **入口**：`setup_logging(level, json_format, path)` 在 `create_app` 最先调用；`get_logger(name)` 取 `finharness.*` 命名空间下的 logger。仓库此前没有任何 `logging` 设施，因此这是唯一定义处，避免日志平台因裸文本无法做字段级过滤。
- **JSON 字段**：`ts / level / logger / msg`，加上条件出现的 `trace_id / session_id / conversation_id / turn`，以及调用方经 `extra=` 附加的任意字段。`JsonFormatter` 对附加字段按键名脱敏后再序列化。
- **trace_id 贯穿**：`trace_id` 在请求入口生成（`tr_<hex16>`），由 `ContextVar` 承载（`context.py`）。`asyncio.create_task` 会复制 context，因此引擎任务与它派生的所有日志自动携带同一个 id——**无需把 id 逐层传递**。
- **关键节点**：请求开始（`request_start`）、工具入参摘要（`tool_call`，脱敏后）、LLM 重试（`llm_retry`，含 `retry_index`/`delay_s`/`error`）、失败（`request_error`，含分类后的 `error_type`）。
- **脱敏规则**（`redact.py`）：
  - **键名**：归一化（小写、去 `-`/`_`）后精确匹配或按 `_SECRET_SUFFIXES` 后缀匹配。因此 `api_key`/`access_token`/`x-api-key`/`apiKey` 命中，而 `max_tokens`/`budget_tokens`/`input_tokens` **不命中**（它们不是凭据，误伤会让 token 指标从日志里消失）。
  - **值模式**：`Bearer …`、`sk-…`、`tvly-…`，以及"≥40 位且至少含一个数字"的随机串。最后一条要求含数字，避免把无空格的长文本误判为密钥。
  - **嵌套**：递归到 6 层，更深的结构替换为 `"<truncated>"`，不会展开成巨量输出。

**3.14.2 指标（metrics.py）**

在 `/metrics` 以 Prometheus 文本格式暴露，仅在 `observability.metrics.enabled=true` 时注册路由。

| 指标 | 类型 | 标签 | 用途 |
|---|---|---|---|
| `agent_request_duration_seconds` | Histogram | `model`, `status` | 请求耗时，出 P50/P95/P99（桶覆盖到 300s） |
| `agent_request_errors_total` | Counter | `error_type` | 按 `token_limit`/`llm_timeout`/`tool_failure`/`auth_error`/`rate_limit`/`server_error`/`provider_error` 分类 |
| `llm_tokens_total` | Counter | `model`, `kind`(input/output/cache_hit/cache_miss), `call_type` | 成本直接来源 |
| `agent_tool_calls_total` | Counter | `tool`, `status` | 调用量与成功率，定位脆弱工具 |
| `agent_tool_duration_seconds` | Histogram | `tool` | 工具耗时直方图 |
| `agent_llm_duration_seconds` | Histogram | `model`, `call_type` | 单次模型调用耗时 |
| `agent_llm_first_token_seconds` | Histogram | `model`, `call_type` | 首 token 延迟（体感指标） |

- **自建 `CollectorRegistry`**，不用 prometheus_client 的全局默认 registry：测试会多次 `create_app`，复用全局 registry 会在第二次注册时抛 `Duplicated timeseries`。
- **`call_type` 区分开销去向**（`main` / `compaction` / `subagent` / `distill`）。压缩摘要、跨对话记忆蒸馏与子 Agent 的 token 此前**完全不计入**会话成本，现在以各自 `call_type` 出现在 `llm_tokens_total` 里：主循环只在自己的轮次边界发一次 `main`，压缩经 `AutoCompactor.on_usage` 回填，子代理经 `Coordinator._account` 汇入总数——**不重不漏**。LTM 蒸馏（`EpisodeDistiller._extract`）发生在对话之外的后台任务里，因此不并入某个会话的 `usage`，只以 `call_type=distill` 单独出现在指标中（它的成本属于"记忆维护"，不是任何一次提问的开销）。
- **治理拦截不算失败**：`denied`/`blocked`/`loop_guard`/`not_activated` 出现在 `agent_tool_calls_total`，但不计入 `tool_failure`，否则"哪个工具最脆弱"会被权限拒绝污染。

**3.14.3 追踪（tracing.py）**

用 LangSmith 的**低层 `RunTree` API**，不引入 LangChain（本项目未使用 LangChain）。Span 层级按 OpenTelemetry 语义设计，将来加 OTLP 导出器时插桩代码无需改动。

```
request (chain, finharness.turn)     model, mode, status, reason, usage
├─ llm (llm, llm.main)              model, call_type, inputs(tool_count [+messages*]), outputs(usage)
├─ tool (tool, tool.<name>)         tool, call_id, args* , status
├─ llm (llm, llm.compaction)        压缩摘要调用，call_type=compaction
├─ llm (llm, llm.distill)           LTM 蒸馏调用（情节+语义同一次，后台，call_type=distill，见 §3.6.4「4.1」「4.2」）
└─ request (chain, finharness.subagent)
   ├─ llm (llm.main → subagent)     子代理的模型调用
   └─ tool (tool.<name>)
```

（`*` 仅在 `capture_payloads=true` 时附带，且已脱敏截断。）

- **父 Span 用 `ContextVar` 栈维护**，因此嵌套与并发工具调用各自独立，调用方无需显式传 parent。
- **`post()` 丢给后台线程**（单例 `ThreadPoolExecutor`）。流式循环里只做内存中的 `end()`，网络上报异步完成——这是追踪不拖慢流式响应的关键。
- **`run()` 的边界归属**：请求根 Span 由 `AgentLoop.run` 持有（服务端、eval、脚本共同边界），服务端只在 `chat_stream` 绑定 trace id，不再另开 Span，避免请求耗时重复计数。子代理的 `run()` 以 `emit_metric=False` 开 Span，因此不计入请求级直方图。

**3.14.4 配置（config/settings.py）**

```jsonc
"observability": {
  "logging": { "level": "INFO", "json_format": true, "path": null,
               "capture_payloads": false, "max_payload_chars": 4000 },
  "metrics": { "enabled": false },
  "tracing": { "enabled": false, "backend": "langsmith", "project": "finharness",
               "env_key": "LANGSMITH_API_KEY", "capture_payloads": false }
}
```

- 默认全关：核心依赖不含 `prometheus-client`/`langsmith`，只有日志（纯标准库）始终可用。
- 环境变量走 `_ENV_FIELDS` 白名单，形如 `FINH_OBSERVABILITY_LOGGING_LEVEL`、`FINH_OBSERVABILITY_METRICS_ENABLED`、`FINH_OBSERVABILITY_TRACING_ENABLED`。
- `logging.path` 相对路径按 `settings.json` 所在目录解析（与 `audit.log_path` 一致）。
- **启动期快速失败**（`validate_runtime`）：`metrics.enabled` 但缺 `prometheus-client`、`tracing.enabled` 但缺 `langsmith` 或 `env_key` 为空、或 `logging.path` 父目录不可写，都直接抛 `SettingsError`。宁可启动即报错，也不要让运维方以为正在采集、实际什么都没上报。

**3.14.5 与审计的关系**

审计（`hooks/audit.py`）与日志是两件事，但共享两样东西：`redact` 脱敏规则，以及 `trace_id`。因此一次对话的**审计行与日志行可用同一个 id 互检**。审计仍然是"始终开启、仅追加、不可移除"的治理记录（ADR-5），观测层可以整体关闭而不影响它。

**3.14.6 运维脚手架（ops/）**

- `ops/prometheus/prometheus.yml`：抓取 `host.docker.internal:8000/metrics`。
- `ops/grafana/provisioning/`：Prometheus datasource + dashboard provider。
- `ops/grafana/dashboards/finharness.json`：六个面板（请求 P50/P95/P99、按类型错误率、token 速率与调用类型、工具调用量与失败率、首 token P95、模型调用 P95），带 `model` 变量。
- `docker-compose.observability.yml`：一键起 Prometheus + Grafana（`extra_hosts` 处理 Linux 上的 `host.docker.internal`）。

用法：以 `observability.metrics.enabled=true` 启动应用 → `docker compose -f docker-compose.observability.yml up -d` → Grafana `http://localhost:3000`（admin/admin）面板已自动装载。

**3.14.7 运行轨迹持久化与监控平台（自建）**

Grafana/Prometheus 覆盖的是"速率与分位"这类聚合信号，看不到**一次运行内部**发生了什么：模型每一步怎么想、调用了什么工具、工具返回了什么、哪一步开始跑偏、为什么停下或交付。这一层由自建 trace 库补齐，与 Prometheus 互补而非替代。

**存储（`observability/trace_store.py`）**——单个 SQLite（默认 `state/trace.db`，WAL），四张表：

| 表 | 一行 = | 关键列 |
|---|---|---|
| `trace_runs` | 一次运行 | input / answer / status / reason / succeeded / rounds / tool_calls / tokens / per_agent / citations / plan / 起止与耗时 |
| `trace_rounds` | 一个轮次 | thought 全文 / actions（工具名 + 脱敏 args）/ observations（工具名、ok、error、返回预览）/ tokens / llm 耗时 / **phase + revision**（记录该轮时的 FSM 阶段与修订号） |
| `trace_states` | 一次 FSM 状态转换 | run_id（trace 运行 id）/ agent_run_id（FSM 运行身份，resume 时不变）/ revision / turn / phase / created_at / payload（公共状态视图全文） |
| `trace_events` | 一个非 `text_delta` 事件 | kind / turn / payload（tool_status、tool_activated、context_compacted、context_routed、**plan_progress 跑偏**、**loop_guard 重复调用**、interactive_request、answer、error、done、state） |

写入纪律：args 走 `redact.summarize_args` 脱敏；`capture_payloads=false` 时 thought/answer/preview 截断到 2000 字符；**所有写入吞错**——trace 落库失败绝不阻断对话。`retention_days` 超期的运行由 lifespan 中的小时级后台任务清理（四张表一并删除）。

**实时落库**：`trace_rounds` 与 `trace_states` 都在运行**进行中**写入，进程崩溃不会丢掉已发生的轮次与状态。轮次经 `OutputSink.record_round`（引擎的可选钩子，`AgentLoop._record_round` 每完成一轮调用一次）落到 `TraceStore.record_round`；状态则因 `TraceStore.record_event` 识别 `kind=="state"` 而顺带写入 `trace_states`。实时写与 `finish_run` 的批量写就同一 `(run_id, turn)` / `(run_id, revision)` 用 `INSERT … ON CONFLICT DO UPDATE` 幂等共存（`trace_rounds` 的批量写用 `COALESCE` 保留实时写下的 phase/revision），因此服务端实时路径与 eval 的用例结束批量重放自动同构。

**接线**：`server/api.py` 在请求入口 `start_run`，`QueueSink` 旁路记录每个非文本事件并实时落轮次，`done`/异常/停止/断连四条收尾路径统一 `finish_run` 并把 `AgentTurnOutcome.trace` upsert 进 `trace_rounds`；`eval/runner.py` 以 `source=eval` 落同一张库，使线上对话与评测运行共享观测面。

**每步 agent 的 state**：`trace_states` 把 FSM 的每一次合法转换提升为一等、可查询的观测产物（`engine/state.py` 的 `AgentState` 每次转换 revision 单调递增）。它与 `trace_events` 中的 `state` 行同源，但按 revision 结构化，使阶段时间线、转换次数与步数成为可直接查询的量；`trace_runs` 与 `trace_states` 以 `run_id` 关联，`agent_run_id` 把显式 resume 产生的多段运行串回同一次 agent 运行。

**八项指标（`TraceStore.metrics_summary`）**：

| 指标 | 公式 |
|---|---|
| 任务完成率 | succeeded runs ÷ 总 runs（附 status/reason 拆解） |
| 工具调用次数 | `tool_status(status=started)` 计数，支持按工具分组 |
| 平均执行步数 | avg(`trace_runs.rounds`) |
| **平均状态步数** | avg(每运行 `trace_states` 行数)，附 **总状态步数** total_states；只计有状态记录的运行 |
| 工具失败率 | failed ÷ started，**剔除 verdict=denied/blocked/loop_guard**（拦截不是失败） |
| 重复调用率 | `loop_guard` 事件数 ÷ started |
| 安全拦截次数 | verdict ∈ {denied, blocked} 的计数 |
| 超时率 | 工具 timeout ÷ started |

另附每工具失败榜与"首次跑偏轮次分布"（`plan_progress` drift 首现 turn）。

**查询 API（`server/trace_api.py`）**：`GET /v1/trace/runs`（分页 + 过滤）、`GET /v1/trace/runs/{run_id}`（完整 run + `rounds_trace` + `events` + **`states`**）、`GET /v1/trace/metrics`，另有 `GET /v1/trace/status`。权限统一为 `users.role='admin'`（`require_admin` 依赖，与 `/v1/admin/*` 共用一处语义）。

**可用性与权限是正交的两个状态**，前端必须能区分，否则运维方只会看到一个无信息量的"加载失败"：

| 情形 | 数据端点 | `/status` |
|---|---|---|
| 未登录 | 401 | 401 |
| 已登录但非管理员 | 403 | 200（`is_admin:false`） |
| 管理员但 `enabled=false` | **503**（detail 含开启方法） | 200（`enabled:false`） |
| 正常 | 200 | 200 |

因此路由器**始终挂载**：未启用时返回 503 而非 404。前端 `MonitorView`（现并入管理页「运行监控」标签）先查 `/status` 再决定渲染数据、显示开启指引，还是显示无权限提示。

**配置**：`observability.trace_store`——`enabled`（默认 false）、`db_path`、`capture_payloads`、`retention_days`。环境变量 `FINH_OBSERVABILITY_TRACE_STORE_*`。纯标准库，无需 `observability` extra。旧字段 `admin_users` **已弃用**：仅为旧 settings.json 兼容保留，不再参与任何鉴权判断。

**用量账本（`observability/usage_store.py`，`state/usage.db`）**：每轮对话一行的 token/轮次记录——`user_id`、输入/输出/缓存命中 token、耗时、终态。与 trace 的分工：trace 是**质量观测**（可选、含正文、90 天保留期），账本是**计费口径**（永远开启、只有元数据、永久累积）；trace 关闭时账本照记。写入与 `/v1/ready` 检查同 trace store 的纪律（吞错旁路 / ping）。管理员页的用户用量与汇总卡片从这里聚合。

**前端**：管理页（`frontend/src/components/AdminView.tsx`）承载「用户总览」与「运行监控」两个页签；工作台顶栏的「管理」入口仅管理员可见（按 `/v1/auth/me` 的 `role` 渲染）。

**前端**：工作台顶栏「运行监控」切换进入自建监控页（`frontend/src/components/MonitorView.tsx`），两个页签——指标面板（八项指标卡片 + 停止原因分布 + 每工具失败榜）与 Trace 浏览器（run 表格 → 抽屉内**阶段时间线** + 逐轮时间线，跑偏点高亮）。阶段时间线由 `detail.states` 经 `lib/agentState.ts` 的 `buildAgentStateTimeline` 构建（hydrate→thinking→tooluse→…，每段时长取相邻 `created_at` 之差）。沿用 `AgentTrace` 的时间线观感，不引入图表库与路由库。「运行监控」入口与「管理」同源门控在 `users.role='admin'` 上：普通用户顶栏只保留工作台；视图切换为内存 state，非管理员身份下残留的 monitor/admin 视图会自动回落到工作台。`MonitorView` 内的「无监控访问权限」三态分支仍保留，作为后端 403 兜底的前端呈现。
