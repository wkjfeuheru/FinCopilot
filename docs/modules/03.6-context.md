### 3.6 context/ —— 上下文工程

**3.6.2 会话状态 ResearchContext（session.py）**

```python
@dataclass

    seq: int; action: str; tool_hint: list[str]; skill_hint: list[str]
    dep: list[int]; status: str      # pending | done | fail | skipped

@dataclass
class Plan:
    plan_id: str; goal: str; steps: list[PlanStep]; revision: int = 1

@dataclass

class ResearchContext:

    conclusions: list[Conclusion]

    loaded_tools: list[str]       # active_tools 集合（懒加载激活后加入）
    # 消息与 token 记账由 Loop 专属字段持有（不暴露给上层）
    def append_user(self, text): ...; def append_tool_result(self, tr): ...
    def add_conclusion(self, text, cids): ...    # record_conclusion 工具写入
    def mark_plan_step(self, seq, status): ...   # update_plan_step 工具写入
    def plan_digest(self) -> str: ...            # 渲染 进度 done/total + 每步状态 + 依赖状态
```

- **计划回写面（2026-09）**：`add_conclusion` / `mark_plan_step` 由 META 工具 `record_conclusion` /
  `update_plan_step` 调用（docs 03.4.1、03.3.9）。此前二者无生产调用者，步骤状态恒为 `pending`、
  结论面恒空；现由模型在每完成/放弃一步、每形成结论时回写，`plan_digest()` 首行给出 `进度 done/total`，
  每步渲染依赖的当前状态（`依赖：1✓,2○`）。**仍为软约束**：只回写与渲染，不阻断任何调用。
- 追问复用规则：追问中出现既有 `symbols` 成员 → 意图路由提示模型复用 cids（提示词写入：同标的数据优先引用 cit_xxxx，避免重复取数）；`ctx.plan` 为任务锚点，compaction 时最高优先级保留。
- REPL `/plan on|off` 切换 `ctx.planning_enabled`：off 时系统提示删除"复杂问题先 research_plan"路由。

**3.6.3 Auto-Compaction（compaction.py）**

> 实现进度：**已落地**（`context/compaction.py` + `context/memory/working.py`）。与原设计的差异记录如下。

- 触发：每轮请求发出前检查"下一次请求体积"是否达 `compaction_ratio × context.context_window_tokens`。窗口值来自配置（**provider 不暴露窗口**，故新增 `context.context_window_tokens`，默认适配 deepseek-chat）。
  - **轮次上限与 token 阈值并列**：token 阈值只管住"窗口有多大"，管不住"有多少轮"。轮次多但每轮很小的长期陪伴式对话永远触不到 token 阈值，历史会无限加长——那同样是内存。`context.max_window_rounds`（默认 40）超过即压缩，`WorkingMemory._rounds_to_keep()` 同值封顶（否则按预算能"全部留下"、边界为 0，压缩空转）。
- 计数：**用 tiktoken 实算**（`cl100k_base`），词表缓存定向到 `data_cache/tiktoken/` 并在启动预热——首次获取约需 1–2 分钟，放系统 temp 会因清理而反复重下。tiktoken 不可用时回退文档的 `len//1.7` 估算，并如实标记为估算值。
- 压缩动作：
  1. 保留：ResearchContext 全部、`ctx.plan`、结论列表、最近 2 轮对话原文。
  2. 对中间过程对话调 `summarize()`（复用会话自身 provider，固定模板，drain 流式输出为完整文本——provider 只有流式接口）。
  3. 摘要作为单条 user 消息占位注入，并在摘要头部注明"此前取过 N 份数据、引用为 …"，**保证数据仍可回溯**（缓存与 citation 未受影响）。
  4. 压缩前后体积与耗时写审计日志（action=compact）。
- **两条实现要点（原设计未覆盖）**：
  - **"轮"按模型往返计，不按 user 消息计**。长研究任务只有一条 user 消息；若按 user 计数则永不触发压缩——恰在最需要时失效。
  - **切点必须落在 assistant 帧上**。若切在 tool_result 与其 assistant 帧之间，会留下"未被声明的 tool_result"，OpenAI 兼容端点直接返回 400。此项由真实 smoke 发现，已加回归测试钉死。
- 逐级收紧：若保留 2 轮后仍超预算（单轮本身很大），依次降到 1 轮、0 轮，确保压缩后**确实**回到预算内。
- 幂等与安全：压缩仅发生在 turn 间隙；摘要失败（模型调用异常）→ 退化为"计数式降级摘要"（只保留起始目标与轮次计数，**必须小于被替换内容**），记录 warning，绝不阻塞会话。
- 双指标：`done` 事件同时给出累计 `usage`（账单口径，压缩不影响）与 `window_tokens`（当前窗口占用，压缩的目标）。两者不可混用。

**3.6.3.1 会话重载的有界加载（内存封顶）**

长对话的完整记录可能有几百轮、每轮都带工具结果。若在会话首轮把整份历史读进内存，
重载峰值就等于全量历史（压缩只在之后才把它裁回去）。因此 `MemoryStore.load_messages`
支持 `recent_rounds`，只回放最近 `context.max_loaded_rounds`（默认 200）轮：

- **切点落在 assistant 帧上**（与压缩同一条硬约束），绝不产生孤儿 `tool_result`。
- **安全阀**：只有被跳过的前缀**确实已被 `summary_segments` 覆盖**时才截断加载——摘要才是
  那部分历史的载体。覆盖不足则回退全量加载（此类对话 token 很小，或下一轮压缩即折叠前缀，
  之后重载自然有界），绝不做无声的遗忘。`MemoryStore.count_covered_prefix()` 判断连续覆盖，
  中间有洞即视为未覆盖到洞之后。
- **序号对齐**：截断后设 `memory.discarded = 跳过的条数`，使后续压缩的 `seq_from/seq_to`
  与真实消息序号一致；否则会从 1 重数，把已覆盖的区间再摘要一遍。

同源的容量封顶：`CitationRegistry.restore()` 与 `register()` 共用上限（长对话的引用史
不再无界重载）；`AgentLoop.compactions` 只留最近若干条并另用累计计数上报；
`ResearchContext.conclusions` 内存保留最近 `CONCLUSION_MEMORY_LIMIT` 条（落库不受影响，
且新增结论经 `pending_conclusions` 逐轮写出，避免每轮重写整份列表）。

**3.6.4 记忆机制（memory/）——工作记忆 / 短期记忆 / 长期记忆三层**

> **实现状态：已落地，但形态与下文原始设计有差异。** 以本节开头的说明为准，下文各条保留为设计依据。
>
> **最终记忆分层**（`context/memory/`）：
>
> | 层 | 载体 | 作用域 | 内容 | 注入方式 |
> |---|---|---|---|---|
> | L1 工作记忆 | 内存，`working.py` | 对话内·窗口 | 最近若干轮**原文**（按 token 预算保留，轮数为下限） | 直接进请求 |
> | 摘要层 | 内存+库，`summary.py` | 对话内 | **分段累积**的更早历史摘要，段含覆盖的消息区间与**取数台账** | 经 `state_block()` 进**请求末尾状态消息** |
> | L2 短期事件 | 内存环，`short_term.py` | 对话内 | 仅两类：**取数事件**（subject + 数据指针）、**结论事件** | 经 `state_block()` 进**请求末尾状态消息** |
> | 原文持久化 | SQLite `messages` 表 | 对话内 | 全部消息，**可按 id 取回** | 不注入，供恢复与追溯 |
> | 结论/标的索引 | `conclusions` / `conversation_symbols` 表 | **对话内（隔离）** | 结论 + cid、标的池 | 同上（带形成日期） |
> | 用户偏好 | `ltm_facts`（`kind='preference'`） | **全局（不隔离）** | 跨对话长期有效的偏好；原 `notes` 表已并入 | 同上（【用户偏好】区块） |
> | **LTM 情节记忆** | `ltm_episodes` 表（`memory/distill.py` 蒸馏，`server/distill_sweeper.py` 调度） | **跨对话·按用户** | 三类情节：`task_result`（每轮结论结构化写入，无 LLM）、`decision`/`excerpt`（懒蒸馏产出），各自带 subject/cid/来源对话溯源 | 首轮注入最近 N 条 + 标的驱动刷新，经 `state_block()` 进**请求末尾状态消息**；另可经 `search_memory` 主动检索 |
> | **LTM 语义记忆** | `ltm_facts` 表（事实/概念/偏好）+ `memory/vector.py` 向量索引 | **跨对话·按用户** | 事实、概念、偏好；`(user_id, key)` UPSERT 覆盖 | 偏好→【用户偏好】；事实/概念→按问题向量召回的【相关知识】；均可经 `search_memory` 检索 |
>
> **状态注入位置（2026-09 修订）**：`state_block()` 曾拼在 **system 提示词**里，导致
> 请求前缀每次都变、历史无法被前缀缓存复用。现改为**请求末尾的临时 user 消息**（不落盘、
> 不进转录、不参与摘要）：请求 = `[静态 system] + 历史 + [状态消息]`。这样历史成为稳定前缀，
> 前缀缓存可复用；状态在最后，模型注意力也最新。窗口测量需显式加上该段
> （`request_tokens(extra_text=…)`），否则压缩会低估窗口。实测见 §3.3.7。
>
> **日期锚点与状态视图标记（2026-09 新增）**：状态块首行固定注入**当前日期**，使模型能判断
> 某个数据期是否即最新已发布期（详见 03.4「数据时效披露」）。该段以 `user` 角色发送，因此
> 带上 `types.STATE_VIEW_META` 元数据标记——否则"最后一条用户消息"的读法（脚本化 provider、
> 测试替身）会把状态块当成用户的提问。子代理不接收该状态（`_state_text()` 按 `call_type`
> 短路）：子代理的输入只有任务文本，不应因共享渲染路径而拿到主会话上下文。
>
> **与原始设计的关键差异**：
> 1. **摘要取代"单条 digest 消息"**：原先每次压缩重写为一条 `Msg.user`，会退化成"摘要的摘要"且谎报说话人；改为分段累积（近期保真、远期归并降级），且随状态块进入**请求末尾的临时消息**，而非伪装成转录里的用户消息。
> 2. **写入时机改为每轮增量**：原设计的"会话结束蒸馏"依赖优雅退出，而 Web 形态下会话靠 TTL 回收、SSE 断线时连 `session_end` 都被跳过——**没有可靠的结束时机**。改为每个 `run()` 结束批量落库（对话与结论同一事务），崩溃最多丢当前轮。
> 3. **作用域分域**：结论/标的/摘要/引用**按对话隔离**；只有**用户偏好全局共享**。
> 4. **`MEMORY.md` 永久不做**：文件视图是为 CLI 设计的，与 Web 形态不匹配；改由只读端点 `GET /v1/memory` 提供查看。
> 5. **偏好全局共享**：偏好不随对话隔离；写入走 `remember_preference` 工具（READ，免确认）。一期只做读取+显式写入、不自动抽取；**二期改为可自动蒸馏**（语义记忆的 `kind='preference'`，与情节共用一次调用），且存储并入 `ltm_facts`（原 `notes` 表已迁移，见 "（4.2）"）。
> 6. **`citations` 必须落库**：恢复时 cid 若重新编号，摘要与结论中记录的 `cit_xxxxxx` 就会指错，因此 `CitationRegistry.restore()` 原样恢复旧 id。
> 7. **L2 收窄为两类事件**：`plan_step` 已由 `ctx.plan` 承载、`calc` 可由取数推出，重复记录只会增加噪声。
> 8. **轮次按模型往返计**（非 user 消息）：长研究任务只有一条 user 消息，按 user 计数会导致压缩永不触发。
> 9. **LTM 情节记忆已复活为按用户作用域的跨对话记忆（2026-09 增补）**：原 L3 的作废理由是"没有可靠的会话结束时机"，而不是"跨对话记忆本身有问题"。新的写入时机绕开了该问题——`task_result` 情节**每轮随结论结构化落库**（无 LLM、与消息同批），`decision`/`excerpt` 由**懒蒸馏**产出，触发点取**双保险**：① 服务端后台扫描器按 `conversations.last_active_at` 判闲置（注意：文档曾说的"每 60s 会话 TTL 回收"在代码中并不存在，注册表是惰性淘汰且无回调，因此扫描器读的是对话表而非会话表）；② 用户开新对话时在 `loop_factory` 里补蒸馏历史对话。只要有用户活动，漏网的蒸馏终会被补上。作用域为 `user_id`（跨对话、不跨用户），保留预算独立于源对话（`ltm.retention_*`，源对话被 prune 不抹掉情节）。检索为**键匹配**（subject/kind/来源对话/时间），与 L2 recall 同一口径，不引向量依赖。
> 10. **语义记忆与向量检索已落地（2026-09 二期）**：`ltm_facts`（事实/概念/偏好，`(user_id, key)` UPSERT 覆盖）与 "（4.2）" 的向量检索（远程 `/embeddings` + Qdrant）。方案是**记录本体留 SQLite、向量只存一份**（配了 Qdrant 只存 Qdrant，`indexed_at` 标记已索引；没配才写 `ltm_facts.embedding` BLOB 做本地余弦），因此治理走单一事实源，核心记忆链路不依赖向量库的可用性；`qdrant-client` 在核心依赖里（惰性导入，未装也能跑，只是无 Qdrant 通道）。偏好二期的治理口径已实现：可自动蒸馏，用户显式声明冲突时直接覆盖（UPSERT 语义保证只有一个版本的真相）。**语义与情节共用同一次蒸馏调用**，因此默认开启不增加 LLM 成本。
>
> **对外身份收敛**：`conversation_id` 是唯一对外标识（隔离与持久化单位）；原先的 `session_id` 降为服务端内部执行窗口（busy/TTL），不再是契约。

**（1）分层总览**

| 层 | 载体（技术） | 作用域 | 生命周期 | 内容 | 对 LLM 可见性 |
|---|---|---|---|---|---|
| L1 工作记忆 | 内存 `list[Msg]`，`WorkingMemory` 维护 | 单会话·上下文窗口 | 存活于 AgentLoop，越界即压缩 | 与模型的**原始往返转写**（user / assistant 帧 / tool_result 帧） | **直接**：每轮全量进请求 |
| L2 短期记忆 | 内存事件环 `list[Episode]`，`ShortTermMemory` | 单会话·跨压缩窗口 | 会话结束随进程回收（结束前蒸馏提交 L3） | 结构化"研究事件"：取数摘要 / 计算 / 计划步骤 / 中间结论 | **间接**：追问命中时召回片段注入 |
| L3 长期记忆（已落地为 LTM，见本节"（4.1）/（4.2）"） | SQLite `data_cache/memory.db` 的 `ltm_episodes` / `ltm_facts` 表（+ 向量索引） | **跨对话·按用户**（不跨用户） | 记忆自包含、独立保留（`ltm.retention_*`），源对话被删不抹掉 | 情节事件（任务结果/关键决策/对话片段）+ 语义条目（事实/概念/偏好），各自带溯源；语义支持向量召回 | **间接**：情节首轮+标的驱动注入，语义按问题向量召回；`search_memory` 主动检索 |

**（2）L1 工作记忆（working_memory.py）——内存 `List[Message]` 动态维护**

```python
class WorkingMemory:

    def __init__(self, *, ctx: ResearchContext, settings: Settings): ...

    def append_tool_result(self, call_id: str, content: str) -> None:

        # openai 兼容端点以 tool role 提交

        ...

    def squash(self, kept: int, digest: Msg) -> None:

        # 并对被裁区间触发 L2 蒸馏（见 L2 写入点）
        ...
```

动态维护规则：
1. **唯一写入口**：`ctx.append_user / append_tool_result` 内部转发到本类（对外签名不变），任何模块不得直接改 `raw`。
2. **增量 token 记账**：每帧 append 后以 §3.6.3 同一估算器（`len//1.7 + 常数`）增量累加 `used_tokens`，O(1)，供 `over_budget()` 判定。
3. **越界不硬切**：`over_budget()` 为真时在 turn 间隙调用 AutoCompactor（§3.6.3 保留策略不变：ctx 状态 + 最近 2 轮原文 + 结论列表）；结果经 `squash()` 落回窗口，digest 仍在窗口内，压缩不丢连续性。
4. **只装"往返转写"**：symbols / plan / conclusions 属会话研究状态（不入 `raw`），避免同一事实双份占用窗口；由 ContextAssembler 以状态块拼装。
5. 生命周期与 AgentLoop 一致：CLI 每进程一份、HTTP 每会话一份（与 §3.12 SessionRegistry 对齐）。

**（3）L2 短期记忆（short_term.py）——会话内结构化事件环**

动机：压缩后若"追问复用"只依赖 digest 单条易含糊；短期记忆把关键事件**结构化落点**，支持按 subject 精确召回、避免重复取数。

```python
@dataclass
class Episode:
    ts: str                              # ISO 时间
    kind: Literal["data","calc","plan_step","finding","conclusion"]
    subject: str                         # 归一化召回键，如 "600519 ROE"（symbol/指标词表）
    summary: str                         # 一句话摘要（含关键数字）
    ref: dict                            # 出处：cids[] / parquet 路径 / cache key（供精读）
    origin: str                          # "tool" | "compaction" | "conclusion" | "manual"

class ShortTermMemory:
    ring: list[Episode]                  # 上限 settings.context.short_mem_cap（默认 200）
    def add(self, ep: Episode) -> None: ...
    def recall(self, subjects: list[str], k: int = 3) -> list[Episode]:
        # 排序：subject 词表命中 → recency 新者优先 → 每 subject 至多 k 条
        ...
```

写入点（蒸馏契约，AgentLoop 侧在以下时机调用 `short_term.add`）：
- `_execute_one` 成功产出数据 → `data`（summary 取裁剪后文本头部；完整数据只留 parquet/cache 指针，**不复制大表**）；
- `calc_*` 完成 → `calc`；`research_plan` 步骤落定 → `plan_step`；模型终答带结论信号 → `conclusion`；
- AutoCompactor 压缩被裁区间 → 逐段摘要 → `origin="compaction"`（与 §3.6.3 digest 生成共享同一次 summarize 调用，不额外计费）。

召回触发：新提问命中 `ctx.symbols` 或词表（追问场景）→ ContextAssembler 在 user 消息后注入"短期记忆相关片段"小节，上限 `settings.context.recall_max_tokens`（默认 400 token）。淘汰：`data` 最旧优先淘汰（数据可由 parquet 缓存重建，价值最低）；`finding / conclusion` 不主动淘汰，随会话结束蒸馏进 L3。

**（4）L3 长期记忆（long_term.py）——SQLite canonical + MEMORY.md 只读视图**

- 取代原"markdown 即存储"：整文件重写式 merge 易错、无法按 subject 查询/去重。升级为 SQLite 单文件（stdlib，与 data_cache 索引同实践，**零新增依赖**）；MEMORY.md 降级为**只读渲染视图**（每次写库后重生成），供 `/memory` 与人工速览。

```sql
-- data_cache/memory.db（canonical store，gitignore）
CREATE TABLE conclusions (           -- 已形成观点（跨会话核心资产）
  id INTEGER PRIMARY KEY, ts TEXT NOT NULL, session_id TEXT,
  subject TEXT NOT NULL,             -- 归一化主体："600519 ROE"
  text TEXT NOT NULL,                -- 结论描述（含关键数字，模型生成）
  cids TEXT,                         -- JSON：依据 citation 列表（防幻觉/可回溯）
  UNIQUE(subject, text));            -- 去重合并键：同结论只记一次，历史不改写
CREATE TABLE symbols (               -- 覆盖标的池（自 conclusions 冗余索引）
  symbol TEXT PRIMARY KEY, name TEXT, first_seen TEXT, last_seen TEXT);
CREATE TABLE notes (                 -- 偏好/约定（入口见下）
  key TEXT PRIMARY KEY, value TEXT, kind TEXT DEFAULT 'preference');
```

- **合并策略**（session_end 统一执行，与 audit 同批）：`conclusions / symbols` 走 `INSERT OR IGNORE` + `last_seen` 更新（只增不改写，时间线可回溯）；`notes` 按 key UPSERT。
- **启动注入（替代原"裁到 40 行"规则）**：会话初始化时按"提及标的 + 最近覆盖"取相关结论（`subject IN (…) ORDER BY ts DESC LIMIT 3`），渲染为 system 小节"历史结论（形成于 {date}，时间敏感数据请重新核对后再引用）"；上限 `settings.context.summary_inject_max_tokens`（默认 600 token；该键原名 `ltm_inject_max_tokens`，名字已让给真正的 LTM 配置段）；其余量化为"覆盖标的池 {N} 个"总览一行，**不全文注入**。用"注入时间窗"控窗口，结论本体永久保留不物理删除（`/memory long` 可翻查）。
- **视图与人工面**：`MEMORY.md` 每次写库后重生成，**不反向 parse**（与 canonical 保持单写者，避免双写打架）；人工改约定走 `settings.json`，记偏好经会话结束蒸馏时由 CLI 列出待写 `notes` 项一次确认（y/N）。

**（4.2）轮次级断点（turn_checkpoints，2026-09）**

一次运行可能被用户主动停止（§3.12.8）或被硬取消。消息与引用按轮持久化已由
`messages`/`citations` 承载，**断点只补那些无法从消息记录重建的执行态**——首要是研究计划
（`ctx.plan` 只活在内存里，进程重启即失），辅以 `partial_answer` 与轮数供界面提示。

```sql
CREATE TABLE turn_checkpoints (     -- 每对话一行，最新覆盖（不保留历史）
  conversation_id TEXT PRIMARY KEY,
  status TEXT NOT NULL,             -- running | stopped | completed
  reason TEXT,                      -- user_stopped | interrupted | loop_detected | …
  rounds INTEGER, turn_index INTEGER,
  plan_json TEXT,                   -- ResearchContext.plan 的序列化（plan_id/revision 原样）
  partial_answer TEXT,              -- 停止时已确立的部分结论
  persisted_seq INTEGER,            -- 落库消息水位（message_seq_range 上界）
  updated_at TEXT NOT NULL);
```

- **覆盖写而非追加**：恢复只需要最新状态，历史断点既无消费者也会无界增长。
- **可继续的判据是 `status='stopped'`**（`TurnCheckpoint.recoverable`）：`running` 是崩溃取证
  （进程被杀死会留下它），`completed` 只是收尾标记，两者都不提供"继续"入口。
- **生命周期**：随 `DELETE /v1/conversations/{id}` 与 `prune()` 一并级联删除——否则被删对话会留下
  一个可"继续"的幻影。新一轮开始时该断点被**消费**（清除），本轮收尾再写入属于它自己的新断点。

**四条数据流**：

| 流 | 时机 | 是否 LLM | 落点 |
|---|---|---|---|
| 写 `task_result` | 每个 `run()` 结束的 `_persist_turn`，与结论同批 | 否 | `ltm_episodes` |
| 写 `decision`/`excerpt` | 懒蒸馏（双保险触发） | 是（`call_type="distill"`） | `ltm_episodes` |
| 注入 | 首轮加载最近 `ltm.recent_episodes` 条 + 每轮按标的池刷新（`refresh_ltm_recall`） | 否 | `state_block()`【跨对话记忆】区块 |
| 检索/治理 | agent 调 `search_memory`；用户经 `GET/PATCH/DELETE /v1/memory[/episodes/{id}]` | 否 | 键匹配查询 |

**蒸馏双保险**（绕开已作废设计的死因"没有可靠的会话结束时机"）：① `server/distill_sweeper.py`
后台任务每 60s 扫 `conversations.last_active_at`，闲置超 `ltm.distill_idle_s` 且未成功蒸馏的对话，
每轮最多 `ltm.distill_batch` 个；② `loop_factory` 在用户开新对话时 `create_task` 补蒸馏该用户
未处理对话（排除当前对话，不阻塞）。失败累加 `attempts`，超 `ltm.distill_max_attempts` 即放弃；
`distiller` 任何异常都不向上抛（与 AutoCompactor 同一纪律）。产出解析见 `_parse_episodes`
（剥代码围栏、取 JSON 数组、坏条目丢弃）；`task_result` 由蒸馏产出会被过滤（每轮已结构化写入）。

**工具**：`search_memory`（READ，免确认）、`update_memory` / `forget_memory`（WRITE，需确认）。
两类记忆共用同一组工具，按 id 前缀区分——`ep_…` 是情节、`fa_…` 是语义条目；
`search_memory` 的 `kind` 参数可筛 `episode`（情节）或 `fact`/`concept`/`preference`。
agent 先检索拿 id，再编辑/删除。

**保留**：`ltm.retention_episodes`（默认 500）/ `ltm.retention_days`（默认 365），按用户独立计算；
蒸馏后触发一次，服务启动时另调 `prune_all_ltm_episodes` 兜底（覆盖"只写 task_result、从不蒸馏"的用户）。

**评测载体**：`evals/cases/m_memory.yaml` 用新的 `chats` 形式声明多对话用例，共享 store 与 user_id；
`EvalCase.all_turns` 把多对话轮次扁平化，使既有 scorer 无需分叉。

**（4.2）LTM 语义记忆与向量检索（已落地，2026-09）**

情节回答"我们做过什么"，语义回答"我们知道什么"。两者共用一次蒸馏调用与一套存储，
但**写入语义完全不同**：情节是只增的（去重键 `(user, kind, subject, summary)`），
语义是**覆盖**的（唯一键 `(user_id, key)`）——一条事实的更新版本必须替换旧表述，
否则注入时会出现两条互相矛盾的记忆。偏好尤其如此。

**表**（与情节同库同表结构）：

```sql
-- ltm_facts：事实 / 概念 / 偏好，UNIQUE(user_id, key) 覆盖语义
--   fa_uid = sha256(user_id|key)[:12]  —— 由 (用户, 键) 确定性派生的对外 id
--   embedding BLOB + embedding_model   —— 本地向量（仅"没配 Qdrant"的部署写入并用于检索；
--   indexed_at                        —— 已索引到外部向量库的标记，配了 Qdrant 的部署靠它）
-- notes 表已并入：set_note/get_notes 现在是 ltm_facts 的薄包装（kind='preference'），
--   初始化时对旧库做一次性 INSERT OR IGNORE 迁移，因此既有部署的偏好无缝延续。
```

**四条流**：

| 流 | 机制 |
|---|---|
| 写入语义 | 与情节**同一次**蒸馏调用产出（提示词一次返回 `{episodes, facts}`）——这是"语义默认开启也不加成本"的前提，故用 `ltm.distill_semantics` 显式关闭 |
| 显式偏好 | `remember_preference` 工具 → `set_note` → facts（`kind='preference'`）；有索引时顺带写向量 |
| 注入 | 偏好经 `notes` 渲染为【用户偏好】（**必须遵守**的指令）；事实/概念经向量召回渲染为【相关知识】（背景知识）。两者分开，因为模型对它们的用法不同 |
| 检索 | `search_memory` 收两类；配了 embedding 时语义部分走向量召回，否则退化为包含匹配 |

**向量存放与检索**（`context/memory/vector.py`）——记录本体永远在 SQLite，
向量只存一份，因此不存在两份真相的同步问题：

| 配置 | 行为 |
|---|---|
| 配了 embedding 端点 + Qdrant url | 向量只存 Qdrant（KNN 带 `user_id` 载荷过滤），`indexed_at` 标记已索引；历史版本写在 BLOB 的存量由启动时 `migrate_local_vectors` 迁入后清空 |
| 只配了 embedding 端点 | 向量写 `ltm_facts.embedding` BLOB，本地暴力余弦（个人工作台数百~数千条为毫秒级） |
| 都没配 | `index.enabled=False`，【相关知识】区块整体不出现，语义条目仍可被键匹配检索 |

- 嵌入客户端是独立的非流式 `/embeddings` 调用（`provider/embeddings.py`）——provider 层只有流式
  chat completions，没有嵌入能力。响应按 `index` 排序还原输入顺序（部分端点乱序返回）。
- 改写条目会**清空该条的向量并撤销索引标记**（旧向量不再代表新表述），由启动回填或下次蒸馏重算；
  删除条目同步清理向量库中的点。
- `confidence`（0~1）由蒸馏提示词要求模型随每条 fact 产出（用户明确陈述给高值、推测给低值），
  落库前校验：非数字或越界一律按 NULL 存——宁可没有置信度，也不要伪造的精确数字。
- 召回按**问题文本**驱动（`refresh_semantic_recall`，每个 `run()` 一次），与情节的标的驱动不同：
  "哪条知识跟当前问题相关"只有拿到问题才知道。注入上限 `ltm.semantic_inject_max_tokens`。
- 依赖是可选的：`qdrant-client` 在 `vector` extra 里；未安装即视为"没配服务"，自动降级。
- 偏好**不受条数上限清理**：被自动删掉会让"记住我的偏好"变成空话。语义保留用
  `ltm.retention_facts`（默认 300）/ `retention_facts_days`（默认 730），只作用于 fact/concept。

**二期治理**：`GET /v1/memory` 的 `facts` 区（含 `semantic_search` 布尔，如实报告本部署是否具备
向量召回）+ `PATCH|DELETE /v1/memory/facts/{fa_uid}`。用户在此改写偏好即"显式声明"，
UPSERT 保证与蒸馏口径冲突时只有一个版本的真相。

**（5）蒸馏与生命周期（贯通链路）**

```text
每轮      提问 → L1.append_user（增量记账）
         → Loop 往返 → L1.append_assistant / append_tool_result
         → 工具/结论落定 → L2.add(data|calc|plan_step|conclusion)   # 结构化事件
         → L1.over_budget → AutoCompactor → L1.squash(kept, digest)
            + 被裁区间逐段摘要进 L2（origin=compaction，共享一次 summarize）
会话结束  优雅退出 → L2 中 conclusion/finding 蒸馏提交 L3（UPSERT）
         → 重渲染 MEMORY.md（只读视图）→ audit session_end
下次启动  L3 按 subject/recency 注入相关结论（限长）→ 新会话可复用历史 cid，避免重复取数
```

**（6）技术选型（人工审阅点）**

| 决策项 | 候选 | 裁定 | 理由 |
|---|---|---|---|
| L1 容器 | `list[Msg]` / `deque[Msg]` | `list[Msg]` | 保序 + 稳定索引，与 ContextAssembler 拼装一致；追加在尾部，无需 popleft |
| L2 载体 | 内存对象 / Redis | 内存 `list[Episode]` | 单进程 asyncio（§1.2）无共享诉求；Redis 引入运维成本，明确不做 |
| L3 存储 | SQLite（stdlib）vs 单 markdown vs JSONL | **SQLite** + markdown 只读视图 | UPSERT 幂等去重、按 subject+recency 查询注入；stdlib 零新增依赖；markdown 并入易脏无去重、JSONL 查询弱 |
| L3 表结构 | 单事件表(JSON 行) vs 关系表 | 关系表（conclusions/symbols/notes） | 读路径固定为"subject 命中 + 时间窗"，关系表可直接 SQL；事件表需扫描反解 |
| L2 召回 | 词表+recency / 向量检索 | v1 词表+recency（`subject` 归一化键） | 会话语料同质、符号命中已够；向量依赖留给真实"语义召回"需求出现后再评估（护栏） |
| L1/L2 持久化 | 每轮落盘 vs 纯内存 | 纯内存（退出时蒸馏提交 L3） | 进程即会话（§1.2），无恢复/回放诉求；落盘只发生在 L3，单写者免对账 |
| LTM 语义检索（二期） | 键匹配 / 向量检索 | **向量检索，向量单一真源**（Qdrant 或本地 BLOB 二选一） | 语义条目（事实/概念）天然没有稳定键，键匹配召回太弱；记录本体留 SQLite，向量库/服务失效只损失语义召回这一层，不丢记忆 |
| LTM 向量存储 | Qdrant / sqlite-vec / 记录内 BLOB | **Qdrant 为主；BLOB 仅限无 Qdrant 部署** | 允许另起服务；配了 Qdrant 就只存 Qdrant（不双写），BLOB 列服务于"只配了 embedding 端点"的轻量部署 |

- **升级护栏**：L2 换向量检索、L3 换外置库（sqlite-vec / Postgres）均需"跨会话语义召回"或"多进程并行写"的真实需求触发，M0–M6 不引入；当前裁定在 DEMO 规模下各载体负载均为常数级（L2 ≤200 事件、L3 数百行）。
- **护栏已触发（2026-09 二期）**："跨会话语义召回"这一真实需求出现，因此为 **LTM 语义记忆**引入了向量检索与 Qdrant（见 "（4.2）"）。注意范围：升级只作用于**新增的语义记忆层**；L2 事件召回仍是词表+recency（会话语料同质，符号命中已够），不受影响。
