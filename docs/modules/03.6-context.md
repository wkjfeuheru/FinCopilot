**3.6.3 Auto-Compaction（compaction.py）**

> 实现进度：**已落地**（`context/compaction.py` + `context/memory/working.py`）。与原设计的差异记录如下。

- 触发：每轮请求发出前检查"下一次请求体积"是否达 `compaction_ratio × context.context_window_tokens`。窗口值来自配置（**provider 不暴露窗口**，故新增 `context.context_window_tokens`，默认适配 deepseek-chat）。
- 计数：**用 tiktoken 实算**（`cl100k_base`），词表缓存定向到 `data_cache/tiktoken/` 并在启动预热——首次获取约需 1–2 分钟，放系统 temp 会因清理而反复重下。tiktoken 不可用时回退文档的 `len//1.7` 估算，并如实标记为估算值。
- 压缩动作：
  1. 保留：ResearchContext 全部、`ctx.plan`、结论列表、最近 2 轮对话原文。
  2. 对中间过程对话调 `summarize()`（复用会话自身 provider，固定模板，drain 流式输出为完整文本——provider 只有流式接口）。
  3. 摘要作为单条 user 消息占位注入，并在摘要头部注明"此前取过 N 份数据、引用为 …"，**保证数据仍可回溯**（缓存与 citation 未受影响）。
  4. 压缩前后体积与耗时写审计日志（action=compact）。
- **两条实现要点（原设计未覆盖）**：
  - **"轮"按模型往返计，不按 user 消息计**。长研究任务只有一条 user 消息；若按 user 计数则永不触发压缩——恰在最需要时失效。
  - **切点必须落在 assistant 帧上**。若切在 tool_result 与其 assistant 帧之间，会留下"未被声明的 tool_result"，OpenAI 兼容端点直接返回 400。此项由真实 smoke 发现，已加回归测试钉死。
- 逐级收紧：若保留 2 轮后仍超预算（单轮本身很大），依次降到 1 轮、0 轮，确保压缩后**确实**回到预算内。
- 幂等与安全：压缩仅发生在 turn 间隙；摘要失败（模型调用异常）→ 退化为"计数式降级摘要"（只保留起始目标与轮次计数，**必须小于被替换内容**），记录 warning，绝不阻塞会话。
- 双指标：`done` 事件同时给出累计 `usage`（账单口径，压缩不影响）与 `window_tokens`（当前窗口占用，压缩的目标）。两者不可混用。

**3.6.4 记忆机制（memory/）——工作记忆 / 短期记忆 / 长期记忆三层**

> **实现状态：已落地，但形态与下文原始设计有差异。** 以本节开头的说明为准，下文各条保留为设计依据。
>
> **最终记忆分层**（`context/memory/`）：
>
> | 层 | 载体 | 作用域 | 内容 | 注入方式 |
> |---|---|---|---|---|
> | L1 工作记忆 | 内存，`working.py` | 对话内·窗口 | 最近若干轮**原文**（按 token 预算保留，轮数为下限） | 直接进请求 |
> | 摘要层 | 内存+库，`summary.py` | 对话内 | **分段累积**的更早历史摘要，段含覆盖的消息区间与**取数台账** | 经 `state_block()` 进**请求末尾状态消息** |
> | L2 短期事件 | 内存环，`short_term.py` | 对话内 | 仅两类：**取数事件**（subject + 数据指针）、**结论事件** | 经 `state_block()` 进**请求末尾状态消息** |
> | 原文持久化 | SQLite `messages` 表 | 对话内 | 全部消息，**可按 id 取回** | 不注入，供恢复与追溯 |
> | 结论/标的索引 | `conclusions` / `conversation_symbols` 表 | **对话内（隔离）** | 结论 + cid、标的池 | 同上（带形成日期） |
> | 用户偏好 | `notes` 表 | **全局（不隔离）** | 跨对话长期有效的偏好 | 同上 |
>
> **状态注入位置（2026-09 修订）**：`state_block()` 曾拼在 **system 提示词**里，导致
> 请求前缀每次都变、历史无法被前缀缓存复用。现改为**请求末尾的临时 user 消息**（不落盘、
> 不进转录、不参与摘要）：请求 = `[静态 system] + 历史 + [状态消息]`。这样历史成为稳定前缀，
> 前缀缓存可复用；状态在最后，模型注意力也最新。窗口测量需显式加上该段
> （`request_tokens(extra_text=…)`），否则压缩会低估窗口。实测见 §3.3.7。
>
> **与原始设计的关键差异**：
> 1. **摘要取代"单条 digest 消息"**：原先每次压缩重写为一条 `Msg.user`，会退化成"摘要的摘要"且谎报说话人；改为分段累积（近期保真、远期归并降级），且随状态块进入**请求末尾的临时消息**，而非伪装成转录里的用户消息。
> 2. **写入时机改为每轮增量**：原设计的"会话结束蒸馏"依赖优雅退出，而 Web 形态下会话靠 TTL 回收、SSE 断线时连 `session_end` 都被跳过——**没有可靠的结束时机**。改为每个 `run()` 结束批量落库（对话与结论同一事务），崩溃最多丢当前轮。
> 3. **作用域分域**：结论/标的/摘要/引用**按对话隔离**；只有**用户偏好全局共享**。
> 4. **`MEMORY.md` 永久不做**：文件视图是为 CLI 设计的，与 Web 形态不匹配；改由只读端点 `GET /v1/memory` 提供查看。
> 5. **`notes` 保留且全局**：偏好不随对话隔离，写入走 `remember_preference` 工具（READ，免确认），只做读取+显式写入，不自动抽取。
> 6. **`citations` 必须落库**：恢复时 cid 若重新编号，摘要与结论中记录的 `cit_xxxxxx` 就会指错，因此 `CitationRegistry.restore()` 原样恢复旧 id。
> 7. **L2 收窄为两类事件**：`plan_step` 已由 `ctx.plan` 承载、`calc` 可由取数推出，重复记录只会增加噪声。
> 8. **轮次按模型往返计**（非 user 消息）：长研究任务只有一条 user 消息，按 user 计数会导致压缩永不触发。
>
> **对外身份收敛**：`conversation_id` 是唯一对外标识（隔离与持久化单位）；原先的 `session_id` 降为服务端内部执行窗口（busy/TTL），不再是契约。

**（1）分层总览**

| 层 | 载体（技术） | 作用域 | 生命周期 | 内容 | 对 LLM 可见性 |
|---|---|---|---|---|---|
| L1 工作记忆 | 内存 `list[Msg]`，`WorkingMemory` 维护 | 单会话·上下文窗口 | 存活于 AgentLoop，越界即压缩 | 与模型的**原始往返转写**（user / assistant 帧 / tool_result 帧） | **直接**：每轮全量进请求 |
| L2 短期记忆 | 内存事件环 `list[Episode]`，`ShortTermMemory` | 单会话·跨压缩窗口 | 会话结束随进程回收（结束前蒸馏提交 L3） | 结构化"研究事件"：取数摘要 / 计算 / 计划步骤 / 中间结论 | **间接**：追问命中时召回片段注入 |
| L3 长期记忆 | SQLite `data_cache/memory.db`（canonical）+ `MEMORY.md`（只读渲染视图） | 跨进程（持久） | 永久（按 subject 去重累积） | 覆盖标的池、已形成结论（含 cid/时间）、偏好约定 | **间接**：启动/换题时注入相关片段 |

**（2）L1 工作记忆（working_memory.py）——内存 `List[Message]` 动态维护**

动态维护规则：
1. **唯一写入口**：`ctx.append_user / append_tool_result` 内部转发到本类（对外签名不变），任何模块不得直接改 `raw`。
2. **增量 token 记账**：每帧 append 后以 §3.6.3 同一估算器（`len//1.7 + 常数`）增量累加 `used_tokens`，O(1)，供 `over_budget()` 判定。
3. **越界不硬切**：`over_budget()` 为真时在 turn 间隙调用 AutoCompactor（§3.6.3 保留策略不变：ctx 状态 + 最近 2 轮原文 + 结论列表）；结果经 `squash()` 落回窗口，digest 仍在窗口内，压缩不丢连续性。
4. **只装"往返转写"**：symbols / plan / conclusions 属会话研究状态（不入 `raw`），避免同一事实双份占用窗口；由 ContextAssembler 以状态块拼装。
5. 生命周期与 AgentLoop 一致：CLI 每进程一份、HTTP 每会话一份（与 §3.12 SessionRegistry 对齐）。

**（3）L2 短期记忆（short_term.py）——会话内结构化事件环**

动机：压缩后若"追问复用"只依赖 digest 单条易含糊；短期记忆把关键事件**结构化落点**，支持按 subject 精确召回、避免重复取数。

```python
@dataclass
class Episode:
    ts: str                              # ISO 时间
    kind: Literal["data","calc","plan_step","finding","conclusion"]
    subject: str                         # 归一化召回键，如 "600519 ROE"（symbol/指标词表）
    summary: str                         # 一句话摘要（含关键数字）
    ref: dict                            # 出处：cids[] / parquet 路径 / cache key（供精读）
    origin: str                          # "tool" | "compaction" | "conclusion" | "manual"

class ShortTermMemory:
    ring: list[Episode]                  # 上限 settings.context.short_mem_cap（默认 200）
    def add(self, ep: Episode) -> None: ...
    def recall(self, subjects: list[str], k: int = 3) -> list[Episode]:
        # 排序：subject 词表命中 → recency 新者优先 → 每 subject 至多 k 条
        ...
```

写入点（蒸馏契约，AgentLoop 侧在以下时机调用 `short_term.add`）：
- `_execute_one` 成功产出数据 → `data`（summary 取裁剪后文本头部；完整数据只留 parquet/cache 指针，**不复制大表**）；
- `calc_*` 完成 → `calc`；`research_plan` 步骤落定 → `plan_step`；模型终答带结论信号 → `conclusion`；
- AutoCompactor 压缩被裁区间 → 逐段摘要 → `origin="compaction"`（与 §3.6.3 digest 生成共享同一次 summarize 调用，不额外计费）。

召回触发：新提问命中 `ctx.symbols` 或词表（追问场景）→ ContextAssembler 在 user 消息后注入"短期记忆相关片段"小节，上限 `settings.context.recall_max_tokens`（默认 400 token）。淘汰：`data` 最旧优先淘汰（数据可由 parquet 缓存重建，价值最低）；`finding / conclusion` 不主动淘汰，随会话结束蒸馏进 L3。

**（4）L3 长期记忆（long_term.py）——SQLite canonical + MEMORY.md 只读视图**

- 取代原"markdown 即存储"：整文件重写式 merge 易错、无法按 subject 查询/去重。升级为 SQLite 单文件（stdlib，与 data_cache 索引同实践，**零新增依赖**）；MEMORY.md 降级为**只读渲染视图**（每次写库后重生成），供 `/memory` 与人工速览。

```sql
-- data_cache/memory.db（canonical store，gitignore）
CREATE TABLE conclusions (           -- 已形成观点（跨会话核心资产）
  id INTEGER PRIMARY KEY, ts TEXT NOT NULL, session_id TEXT,
  subject TEXT NOT NULL,             -- 归一化主体："600519 ROE"
  text TEXT NOT NULL,                -- 结论描述（含关键数字，模型生成）
  cids TEXT,                         -- JSON：依据 citation 列表（防幻觉/可回溯）
  UNIQUE(subject, text));            -- 去重合并键：同结论只记一次，历史不改写
CREATE TABLE symbols (               -- 覆盖标的池（自 conclusions 冗余索引）
  symbol TEXT PRIMARY KEY, name TEXT, first_seen TEXT, last_seen TEXT);
CREATE TABLE notes (                 -- 偏好/约定（入口见下）
  key TEXT PRIMARY KEY, value TEXT, kind TEXT DEFAULT 'preference');
```

- **合并策略**（session_end 统一执行，与 audit 同批）：`conclusions / symbols` 走 `INSERT OR IGNORE` + `last_seen` 更新（只增不改写，时间线可回溯）；`notes` 按 key UPSERT。
- **启动注入（替代原"裁到 40 行"规则）**：会话初始化时按"提及标的 + 最近覆盖"取相关结论（`subject IN (…) ORDER BY ts DESC LIMIT 3`），渲染为 system 小节"历史结论（形成于 {date}，时间敏感数据请重新核对后再引用）"；上限 `settings.context.ltm_inject_max_tokens`（默认 600 token）；其余量化为"覆盖标的池 {N} 个"总览一行，**不全文注入**。用"注入时间窗"控窗口，结论本体永久保留不物理删除（`/memory long` 可翻查）。
- **视图与人工面**：`MEMORY.md` 每次写库后重生成，**不反向 parse**（与 canonical 保持单写者，避免双写打架）；人工改约定走 `settings.json`，记偏好经会话结束蒸馏时由 CLI 列出待写 `notes` 项一次确认（y/N）。

**（5）蒸馏与生命周期（贯通链路）**

```text
每轮      提问 → L1.append_user（增量记账）
         → Loop 往返 → L1.append_assistant / append_tool_result
         → 工具/结论落定 → L2.add(data|calc|plan_step|conclusion)   # 结构化事件
         → L1.over_budget → AutoCompactor → L1.squash(kept, digest)
            + 被裁区间逐段摘要进 L2（origin=compaction，共享一次 summarize）
会话结束  优雅退出 → L2 中 conclusion/finding 蒸馏提交 L3（UPSERT）
         → 重渲染 MEMORY.md（只读视图）→ audit session_end
下次启动  L3 按 subject/recency 注入相关结论（限长）→ 新会话可复用历史 cid，避免重复取数
```

**（6）技术选型（人工审阅点）**

| 决策项 | 候选 | 裁定 | 理由 |
|---|---|---|---|
| L1 容器 | `list[Msg]` / `deque[Msg]` | `list[Msg]` | 保序 + 稳定索引，与 ContextAssembler 拼装一致；追加在尾部，无需 popleft |
| L2 载体 | 内存对象 / Redis | 内存 `list[Episode]` | 单进程 asyncio（§1.2）无共享诉求；Redis 引入运维成本，明确不做 |
| L3 存储 | SQLite（stdlib）vs 单 markdown vs JSONL | **SQLite** + markdown 只读视图 | UPSERT 幂等去重、按 subject+recency 查询注入；stdlib 零新增依赖；markdown 并入易脏无去重、JSONL 查询弱 |
| L3 表结构 | 单事件表(JSON 行) vs 关系表 | 关系表（conclusions/symbols/notes） | 读路径固定为"subject 命中 + 时间窗"，关系表可直接 SQL；事件表需扫描反解 |
| L2 召回 | 词表+recency / 向量检索 | v1 词表+recency（`subject` 归一化键） | 会话语料同质、符号命中已够；向量依赖留给真实"语义召回"需求出现后再评估（护栏） |
| L1/L2 持久化 | 每轮落盘 vs 纯内存 | 纯内存（退出时蒸馏提交 L3） | 进程即会话（§1.2），无恢复/回放诉求；落盘只发生在 L3，单写者免对账 |

- **升级护栏**：L2 换向量检索、L3 换外置库（sqlite-vec / Postgres）均需"跨会话语义召回"或"多进程并行写"的真实需求触发，M0–M6 不引入；当前裁定在 DEMO 规模下各载体负载均为常数级（L2 ≤200 事件、L3 数百行）。
