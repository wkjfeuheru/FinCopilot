# 生产环境隔离与多租户加固方案

> **范围**：本文回答两个问题——① 项目中所谓"沙箱隔离工作区"当前究竟是如何设计的；② 在**多租户、用户不可信**的目标部署形态下，生产环境需要怎样进一步改进。
> **性质**：评估报告 + 分阶段路线图。本文为新增文档，不修改任何代码，也不修改既有文档；与既有文档的偏差集中记录在第 4 节。
> **复核基准**：所有 `file:line` 引用在撰写时按当前 HEAD 逐一核对（含 `src/` 与 `docs/`）。行号会随代码演进漂移，引用时请以函数名为准。

---

## 0. 结论摘要

1. **项目里不存在"沙箱隔离工作区"这个实体。** 没有容器、chroot/jail、受限账户、worker 子进程或命名空间。唯一以 sandbox 命名的 `scan_sandbox()`（`src/finharness/permissions/rules.py:86-96`）在 `src/` 与 `tests/` 中**零调用点**，其导入白名单与标识符黑名单从未执行过。`run_python` 是刻意不发布的（`docs/modules/03.7-governance.md:39`、`README.md:214`）。

2. **当前真实的隔离是四层应用级机制**，全部运行在**同一个进程、同一个 OS 账户、同一套文件系统**内：工具侧路径包含检查、每用户 output 目录、权限门（确认门）、配置护栏。它是"路径白名单 + 确认"，不是"沙箱"。

3. **对照"多租户、用户不可信"，差距是结构性的而非配置性的。** 三个必须优先处理的真实漏洞：
   - **G1 缓存跨租户可读**：`data_for()` 只 scope 了 `output_dir`，`cache_dir` 全局共享；而缓存文件名由请求形状哈希决定，可被同租户推算。
   - **G2 密钥与全部租户数据库与缓存同处一棵 agent 可达的树**（`data_cache/`）：`secret.key`、`users.db`、`memory.db`、`config.db`、`index.db` 全在其中。一次进程内妥协即等于全部租户的供应商 API Key + 全部对话。
   - **G3 超时对阻塞 I/O 无效且读写无体积上限**：阻塞同步 I/O 位于 async 路径，`asyncio.wait_for` 无法中断不 yield 的协程；parquet 读与文件写都没有大小上限。在多租户下这是跨租户 DoS 原语。

4. **正确的边界是内核级隔离**，这一判断文档早已给出（`docs/modules/03.7-governance.md:39`："正确边界是 OS 级隔离（容器/受限账户 + 密钥目录不可达）"）。路线图据此分三阶段：Phase 0 应用层止血（多租户上线前置）、Phase 1 引入进程/容器边界、Phase 2 运营与合规。

5. **一处需要纠正的常见误判**：出站 SSRF 防护**是活的**，不是死代码。`eastmoney_report_adapter.py:161` 默认走 `fetch_pdf_bytes`，私网封禁、逐跳重校验、重定向/时长/体积上限均已生效（详见 G12）。其唯一已知局限是"请求前解析、非 DNS-rebinding 免疫"，与文档一致。

## 1. 现状：现在是怎么设计的

### 1.1 先澄清"沙箱"这个词在本项目里指什么

从代码事实出发，"沙箱"在项目中出现在三个位置，且三者都不是 OS 级沙箱：

| 位置 | 实际是什么 | 是否生效 |
| --- | --- | --- |
| `permissions/rules.py:86-96` `scan_sandbox()` | 对 `run_python` 源码的**静态文本扫描**：import 白名单 + 标识符黑名单 | **未生效**（零调用点） |
| `docs/modules/FinHarness架构与模块详细设计.md:442` `RestrictedExecutor` | 设计文档中的 `exec(compile(...), {"__builtins__": {...}})` 受限内建执行器 | **不存在**于代码中 |
| `permissions/gate.py:60-86` `PermissionGate` | 对**工具调用**的 allow/confirm/deny 裁决（含路径白名单） | 生效 |

换言之：**"沙箱"目前只是一个政策名词 + 一批未接线的常量**。真正的隔离能力由下面四层承担。

### 1.2 真实生效的四层隔离机制

#### 第 1 层：工具侧路径包含检查（强制）

`_resolve_within()`（`src/finharness/tools/generic/files.py:21-31`）对目标 `resolve()` 后要求其落在显式给出的 roots 之内，否则 `ValueError`：

```python
target = Path(raw).resolve()
for root in roots:
    if target == root or target.is_relative_to(root):
        return target
...
raise ValueError(f"路径超出允许范围（仅限 {allowed}）：{raw}")
```

- `read_file` roots = `output/` + `data_cache/parquet`（`files.py:50`）
- `write_file` roots = 同上（`files.py:80`）
- `read_pdf` roots = `output/` + `data_cache/pdf` + `data_cache/parquet`（`tools/generic/pdf.py:52-56`）
- `summarize_document` 复用同一 roots 集合（`tools/meta/summarize.py:178-182`）

因为先 `resolve()` 再判包含，`..` 逃逸与**持久化**符号链接都会被正确拒绝（指向树外的软链解析后落在 roots 之外）。这是当前最有效的一层。

#### 第 2 层：每用户 output 目录 + 属主校验（强制）

`data_for(user_id)`（`src/finharness/server/api.py:289-296`）为每个用户克隆一份 settings，把 `output_dir` 换成 `output/<user_id>`：

```python
user_settings = settings.model_copy(
    update={"paths": settings.paths.model_copy(
        update={"output_dir": settings.paths.output_dir / user_id})}
)
scoped = DataAccess(adapters, cache=data_cache, settings=user_settings)
```

配合的属主校验：
- 产物下载端点按 `output/<user.id>` + `cache/parquet` 复核包含关系（`server/api.py:747-761`）。
- 会话/对话属主不匹配即 404 或 `SessionBusyError`（`server/sessions.py`、`server/api.py`）。
- 确认总线拒绝非属主的确认应答（`server/confirm.py`）。

**关键局限**：`data_for` 只换了 `output_dir`，**`cache_dir` 仍指向全局的同一份**（`api.py:296` 把 `cache=data_cache` 原样传入）。因此 `server/api.py:352` 注释所称"用户之间互不可见"**仅对 output 子树成立，对 cache 子树不成立**——这正是 G1。

#### 第 3 层：权限门（强制 + 启发式混合）

`PermissionGate.check()`（`permissions/gate.py:60-86`）的裁决顺序：

1. **deny 规则优先于一切，包括读类工具**（`gate.py:64-66`）。规则是硬编码的交易意图正则（`rules.py:19-29`），对 `code` 参数与每个顶层字符串参数生效。
2. 读类工具始终 ALLOW（`gate.py:69-70`）。
3. 写类工具若目标落在白名单目录内 → ALLOW，免确认（`gate.py:73-74`）。
4. 模式回退：`AUTO` 放行全部写（`gate.py:77-78`）。
5. 否则请求确认；**无交互通道时拒绝，而不是静默放行**（`gate.py:80-82`）。

两个默认闸门：
- `ReadOnlyGate`（`gate.py:29-39`）只放行 `PermissionLevel.READ`，其余一律 DENY。它是 `AgentLoop` 未注入闸门时的默认值（`engine/loop.py:139`），也是复核子代理使用的闸门（`coordinator/reviewer.py:291`）。**注意它完全不做 deny 扫描**（见 G7）。
- 服务端在 `loop_factory` 中构造 `PermissionGate`（`server/api.py:361-368`），确认经由 SSE + `ConfirmBus` 完成。

#### 第 4 层：配置护栏（强制）

`Settings.validate()`（`src/finharness/config/settings.py:494-503`）两条跨字段约束：

- `allow_remote=false` 时 `server.host` 必须是回环地址；
- `allow_remote=true` 时 `permission.default_mode` **必须**为 `default`（禁止服务端静默自动写入）。

### 1.4 项目自述的信任边界（原文引用）

项目对自身隔离等级的表述是诚实的，报告中所有结论都应与之一致而非相互矛盾：

## 2. 差距：现状与"多租户、用户不可信"之间的风险清单

严重度分三类：**真实漏洞**（在不可信租户假设下可被利用）、**纵深错位**（不单独构成漏洞，但使防线建立在错误的根上）、**工程债**（正确性或一致性问题）。

### 2.1 真实漏洞

#### G1 缓存跨租户可读（严重）

**事实**：
- `data_for()` 只重写 `output_dir`，缓存实例是全局共享的同一个（`server/api.py:289-296`，第 296 行 `DataAccess(adapters, cache=data_cache, ...)`）。
- 三个入口都向 agent 暴露 `data_cache/parquet`：`read_file`（`tools/generic/files.py:50`）、`write_file`（`files.py:80`）、`/v1/artifacts`（`server/api.py:747-750`）；`read_pdf` 还额外暴露 `data_cache/pdf`（`tools/generic/pdf.py:52-56`）。
- 缓存文件名是**由请求形状决定的哈希**：`make_cache_key()` = `sha256(endpoint|normalized-params|data_date)[:16]`，落盘于 `data_cache/parquet/<YYYY-MM>/<key>.parquet`（`data/cache.py:48-53`，布局见 `cache.py:1-4`）。

**可利用性**：租户 A 只要知道某 endpoint 与 params（这些是公开的取数接口形状），即可在本地计算出租户 B 那份 parquet 的文件名，然后用 `read_file` 读出其内容。缓存内含联网检索正文与研报/公告 PDF 抽取文本——即 B 的检索与研报行为及内容。

**为什么这是漏洞而非"共享缓存省空间"**：缓存内容可反推租户的查询与订阅行为，属于跨租户信息泄露；且 `read_file` 与 `/v1/artifacts` 是 agent/HTTP 可达的正式路径。`server/api.py:352` 的注释"因此用户之间互不可见"在当前实现下不成立。

#### G2 密钥与全部租户数据库与 agent 可达的缓存同树（严重）

**事实**：以下全部位于 `data_cache/`（或其下）：

| 资产 | 路径 | 证据 |
| --- | --- | --- |
| 主加密密钥（Fernet） | `data_cache/secret.key` | `server/api.py:223`、`config/crypto.py:22-39` |
| 用户/令牌库（密码哈希） | `data_cache/users.db` | `settings.py:344` |
| 全部租户对话库 | `data_cache/memory.db` | `settings.py:342` |
| 加密后的配置库（供应商 API Key） | `data_cache/config.db` | `server/api.py:222` |
| 缓存索引 | `data_cache/index.db` | `data/cache.py:1-4` |

而 `PermissionGate._cache_dir` 指向**整棵** `data_cache/`（`gate.py:57`）。

**意义**：这正是文档拒绝发布 `run_python` 的核心论证——"不可信内容注入诱导的代码仍可读同用户可读的 `data_cache/secret.key` 与配置库，从而解开供应商 API key"（`03.7-governance.md:39`）。**但这个论证不依赖代码执行**：任何进程内逃逸路径（模板注入、反序列化、未来的插件/脚本工具、依赖链漏洞）都能达到同一效果。当前架构把"最敏感资产"与"agent 最常读写的工作目录"放在一起，使纵深防御无从谈起。

#### G3 超时对阻塞 I/O 无效 + 读写无体积上限（严重，多租户下为 DoS）

**事实**：
- 超时由 `asyncio.wait_for` 实现（`engine/loop.py:1796`）。`wait_for` 只能取消**协作式**的协程；一个从不 yield 的同步调用无法被中断。
- 文件工具在 async 路径内做**阻塞同步 I/O**：`pd.read_parquet(target)`（`files.py:58`）、`target.read_text(...)`（`files.py:61`）、`target.write_text(...)`（`files.py:83`），绘图同理 `figure.savefig`（`tools/fin/chart.py:284`）。
- 读取上限只覆盖文本分支（`MAX_READ_BYTES = 200_000`，`files.py:18,61`）；**parquet 分支无任何字节/行上限**，写入也无内容上限。

**后果**：一个超大 parquet 的读取会**阻塞整个事件循环**，在此期间同进程内其他租户的请求全部停滞；30s 超时只在该调用返回后才触发，形同虚设。在多租户单进程模型下，这是一个跨租户 DoS 原语，而且不需要恶意构造——`read_file` 指向一个正常产出的大文件即可。

#### G4 无租户配额与限速（严重）

**事实**：全仓没有请求级限速。grep 仅命中的 `throttle` 是取数适配器的出站节流（`data/adapters/akshare_adapter.py:167-181`，默认 `data.throttle_seconds=1.0`，`settings.py:118`），它保护的是**上游数据源**，不是本服务。唯一的用量上界是 `context.max_turns=30`（`settings.py:161`）与会话级 busy 锁。

**后果**：单租户可无限发起 turn 与工具调用，耗尽进程/上游/模型配额，影响其他租户。

#### G5 开放注册与登录无限速（严重）

**事实**：
- `auth.allow_register` 默认为 `true`（`settings.py:283`），无邀请码、无审批、无邮箱验证（`server/auth_api.py`）。
- 无登录失败计数/退避/锁定。
- **首个注册者会继承历史数据**：`auth/store.py:177-178` 在用户表原本为空时调用 `claim_legacy(user_id)`，把 `user_id=''` 的存量数据划归该用户。

**后果**：任一能触达服务的人可自助获得一个租户；若有历史存量数据，第一个注册者直接取得它。

### 2.2 纵深错位

#### G6 闸门白名单根宽于工具实际根

`PermissionGate` 用**全局** settings 构造（`server/api.py:361`），于是 `_output_dir` 是全局 `output/`、`_cache_dir` 是整棵 `data_cache/`（`gate.py:56-57`）。而 `_path_in_whitelist` 命中即 ALLOW 免确认（`gate.py:73-74`）。

因此一个指向 `output/<他人目录>/x.txt` 或 `data_cache/users.db` 的写操作，会在闸门处被判为"白名单产物写入、免确认放行"，**随后**才被工具侧 `_resolve_within` 拒绝。结论：不构成越权写原语（第 1 层拦住了），但"是否需要用户确认"这个决策是建立在比实际操作更宽的根上——防线之间的根不一致。

#### G7 `ReadOnlyGate` 完全跳过 deny 扫描

`ReadOnlyGate.check()` 只看 `tool.permission`，不做任何参数扫描（`gate.py:29-39`）。而它是引擎默认闸门（`engine/loop.py:139`）与复核子代理的闸门（`coordinator/reviewer.py:291`）。于是"一个携带下单指令的数据参数"这一确切威胁（`rules.py:1-11` 声明的存在理由），在 `ReadOnlyGate` 下**完全不被检查**。

#### G8 deny 扫描浅且配置未接线

- `scan_args()` 只检查顶层字符串与**一层** list/tuple，**不递归嵌套 dict**（`rules.py:70-83`）。而 `write_report` 的 `sections` 等参数正是嵌套结构，交易意图可藏于其中。
- `PermissionGate.__init__` 接收 `deny_patterns` 并存入 `self._deny_patterns`（`gate.py:50,58`），但 `check()` 调用的是模块级 `scan_text/scan_args`，**从不读取该字段**；`settings.py` 也没有对应字段与 `FINH_*` 映射。因此 `docs/modules/03.7-governance.md:37`"可经环境变量覆盖"的表述不成立。

#### G9 `data_for` 的 shared_data 逃生舱静默关闭隔离

`data_for()` 开头：若注入了 `data_access`，则**所有用户返回同一个 `shared_data`**（`server/api.py:285-286`），每用户 output 隔离被静默关闭。这是测试/本地运行的行为，但该开关没有显式命名，多租户启动时也不会报警。

#### G10 审计是"记录"而非"执法"

- 写审计失败被静默吞掉（`engine/loop.py:1918-1919`，注释即 `审计是尽力而为`）——即"审计不可用"这一事实本身不可观测。
- 全部租户写同一个进程级文件（`settings.audit.log_path`），无租户分流、无防篡改（无哈希链、无只追加外部 sink）。

#### G11 路径检查存在 TOCTOU 窗口

`resolve()` 后按解析结果直接 open/write（`files.py:51,81`），两阶段之间无 `O_NOFOLLOW`/`lstat` 复核。在**敌意本地文件系统**下存在换链竞态。单用户本机风险低；若 Phase 1 引入共享卷或跨租户可写的暂存目录，则该窗口变得可操作。

### 2.3 已正确，必须排除的误报

#### G12 出站 SSRF 防护是活的（非死代码）

初查容易误判为死代码，实际是**已接线的**：
- 调用链：`eastmoney_report_adapter.py:161` 默认 `self._pdf_fetcher = pdf_fetcher or (lambda url: fetch_pdf_bytes(url))`，在 `:364` 被用于抓取研报全文。
- 防护（`data/adapters/pdf_fetch.py`）：`is_blocked_ip`（:62）拒绝 loopback/私网/link-local/组播/保留/不可解析地址（覆盖云元数据 `169.254.169.254`）；`assert_public_host`（:83）解析主机名并校验；请求前校验且**每一跳重定向都重新校验**（:128）；scheme 白名单、重定向次数上限、响应体上限、超时。

因此第 3 节路线图中**不应**安排"补 SSRF 防护"这类条目。唯一保留项是把"请求前解析"升级为"固定对端"以消除 DNS-rebinding 面（P1-5），这与 `03.7-governance.md:50` 记录的已知局限一致。

## 3. 分阶段改进路线图

排序原则：**能消除跨租户可达性的先做**（P0），**需要新边界的随后**（P1），**运营与合规最后收敛**（P2）。P0 全部可在应用层完成，不需要容器，因此可作为"多租户上线"的前置条件独立交付。

### Phase 0 — 止血（应用层；多租户上线前置条件）

#### P0-1 缓存按租户命名空间
- **做法**：`data_for()` 在克隆 settings 时同时把 `data.cache_dir` 换成 `data_cache/users/<user_id>/`；同步修正 `read_file`/`write_file`/`read_pdf` 的 roots 与 `/v1/artifacts` 的 `allowed_roots`，使其从各自 `settings` 派生而非写死。
- **注意**：`LocalCache` 的 SQLite 索引（`data_cache/index.db`）与 parquet 子树需一并迁入用户命名空间，否则索引仍跨租户可见。同时评估共享缓存的收益是否值得保留：若放弃跨租户缓存复用，命名空间隔离最简单；若保留，则须让 `read_file` 只能读到本租户写入过的 key（白名单表）。
- **验收**：存在测试证明——给定租户 A 的会话，无法通过 `read_file`、`read_pdf` 或 `/v1/artifacts` 读到租户 B 产生的任一缓存载荷（按已知 endpoint+params 算出路径后尝试）。
- **代价**：改代码（中等，涉及 `data_for`、三个工具 roots、一个端点）；不改部署。**会牺牲跨租户缓存命中率**，需在报告/文档中明确该取舍。

#### P0-2 闸门与工具同根
- **做法**：`loop_factory` 用 `data_for(user_id)` 返回的那份 scoped settings 构造 `PermissionGate`，而不是全局 `settings`（`api.py:361`）。
- **验收**：指向 `output/<他人>/x.txt` 的写操作不再被闸门判为"白名单免确认"。
- **代价**：改代码（小，单点）。

#### P0-3 密钥与租户数据库迁出 agent 可达树
- **做法**：新增 `paths.state_dir`（如 `state/`），把 `secret.key`、`users.db`、`memory.db`、`config.db` 迁入；`data_cache/` 只保留可缓存载荷。可选：给 `state/` 设置更严格的文件权限，并在启动时校验其不在工具 roots 的任何祖先链上。
- **验收**：断言 `data_cache/` 子树内不存在任何密钥或数据库文件；且 `_resolve_within` 的任一 roots 都不是 `state_dir` 的祖先。
- **代价**：改代码（小）+ **改配置/迁移**（现有部署需要数据搬迁脚本，需在文档中给出迁移步骤）。

#### P0-4 真超时 + 体积上限
- **做法**：把文件工具的阻塞 I/O 移入 `asyncio.to_thread`（或专用线程池），使 `asyncio.wait_for` 能真正取消；给 parquet 读加字节/行上限（对齐 `MAX_READ_BYTES` 的思路）；给 `write_file`/`write_report` 加内容上限。
- **验收**：对一个超大 parquet 的读取不再阻塞事件循环超过配置超时；超限读写在超时/上限处被明确拒绝并审计。
- **代价**：改代码（中等）。
- **备注**：若未来 P1-2 把工具执行移入独立 worker 进程，则此处的超时可改为"杀进程"，但 P0-4 仍是必要的（进程内也不能阻塞事件循环）。

#### P0-5 注册与登录加固
- **做法**：`allow_register` 默认改为 `false`（或引入邀请码/审批）；登录加失败计数 + 指数退避 + 锁定；把 `claim_legacy` 的"首注册者继承存量数据"改为显式管理动作或直接移除。
- **验收**：默认配置下无法自助注册；连续失败登录被节流；存量数据归属不再由"谁先注册"隐式决定。
- **代价**：改代码（小-中）+ 改默认配置。

#### P0-6 每租户配额与限速
- **做法**：在 API 层加每租户的并发会话数、单位时间 turn/工具调用/token 预算，超限返回 429；与既有的 `context.max_turns` 形成面与点两层约束。
- **验收**：单租户压测不导致其他租户的请求延迟显著恶化（阻塞 I/O 修好后此项才可稳定验证，故与 P0-4 同批）。
- **代价**：新增模块（中等）。

#### P0-7 修 deny 扫描
- **做法**：`scan_args` 递归遍历全部嵌套 dict/list/tuple；把 `deny_patterns` 接线到 settings（含 `FINH_*` 映射）或删掉该死参数并同步修正文档；让 `ReadOnlyGate` 复用 deny 扫描（`ReadOnlyGate` 的语义是"只读"，不是"不检查"）。
- **验收**：嵌套结构内的交易意图命中被拒；`ReadOnlyGate` 下携带交易指令的参数同样被拒。
- **代价**：改代码（小）。

#### P0-8 审计不可吞 + 租户分流
- **做法**：审计写失败改为计数 + 告警（不再 `pass`）；审计行带 `user_id` 并按租户分流存储或至少建索引；引入最小防篡改（哈希链或只追加外部 sink）。
- **验收**：模拟审计写入失败可被观测到；可按租户独立检索审计。
- **代价**：改代码（中等）。

### Phase 1 — 引入内核级边界

> 这一阶段正是文档早已指向的"正确边界"（`03.7-governance.md:39`）。它的目的不是马上启用 `run_python`，而是让**现有的文件与网络工具**也运行在真正的边界内。

#### P1-1 workspace 契约
- 定义唯一可写区 `workspaces/<user_id>/<conversation_id>/`；应用代码只读挂载；密钥目录不挂载。
- 产出**契约文档**（哪些路径必须存在、哪些必须不可见），作为 P1-2/P1-3 的验收依据。

#### P1-2 执行沙箱
- 每会话或每用户一个 worker 进程/容器；以非 root 受限账户运行；只读 rootfs；`no-new-privileges`；seccomp 默认拒绝；cgroup v2 限制 CPU/内存/pids/io；网络默认关闭或仅经 egress 代理。
- 这是把 G2 从"靠路径检查"升级为"靠命名空间不可见"——即文档所说的"密钥目录不可达"。

#### P1-3 文件工具改走沙箱 broker
- `read_file`/`write_file`/`read_pdf` 经沙箱内的 workspace 视图访问文件；路径白名单从"应用层检查"升级为"命名空间内不存在"。
- 这一步同时消除 G11 的 TOCTOU 窗口（挂载视图内无法换链到树外）。

#### P1-4 若启用 `run_python`
- 仅在 P1-2 沙箱内运行；`scan_sandbox` 保留为**防天真注入的旁路**，文档明确其非安全边界（与 `03.7-governance.md:39` 立场一致）。

#### P1-5 出站网络收窄
- DNS 解析后以 IP 直连并固定 Host 头，消除 DNS-rebinding 面（G12 的唯一保留项）；引入 egress 白名单；每租户出站配额。

#### P1-6 关闭 `data_for` 逃生舱
- 给 `data_access` 注入加显式的"单租户模式"开关；多租户启动时若检测到注入即拒绝启动（对齐 G9）。

### Phase 2 — 运营与合规

- **应用容器化**：非 root、只读 rootfs、drop capabilities；镜像扫描 + SBOM + 依赖锁定。
- **暴露面收敛**：TLS 终止 + `secure_cookie=true`；把 `/metrics`、`/v1/health` 移入内网/mTLS 或独立端口（G14）。
- **告警与演练**：对拒绝率、配额超限、审计写失败、确认超时建立告警；建立越权访问的定期渗透回归用例（把 P0-1/G1 的验收测试纳入常规回归）。
- **数据生命周期**：租户级导出/删除（遗忘权）必须覆盖缓存与审计；保留期配置化。
- **威胁模型文档化**：把"单用户本地工具 / 演示级隔离"改写为多租户威胁模型，逐条标注哪些是**强制边界**（命名空间、挂载、配额）、哪些是**启发式护栏**（deny 正则、静态扫描）。

## 5. 结论与验收

### 5.1 一句话结论

**现状没有"沙箱隔离工作区"**——隔离由应用层的"路径白名单 + 每用户 output 目录 + 确认门"承担，而全系统共用**一个进程、一个 OS 账户、一棵含密钥与全部租户数据库的 `data_cache/`**。在"多租户、用户不可信"的目标下，G1/G2/G3 是可被利用的真实漏洞，必须在对外开放前修复；Phase 1 的进程/容器边界才是文档早已指向的正确边界。

### 5.2 本报告的验收标准

报告以**可执行性**为准绳，逐条自检：

1. **每条风险有唯一证据**：14 条（G1-G14）均给出至少一个 `file:line` 或文档锚点，见 2.5 汇总表。
2. **每条风险可复现验证**：P0 各项均给出具体验收方式（尤其是 P0-1 的跨租户读取尝试、P0-4 的大文件阻塞测试）。
3. **每条风险有 Phase 归属**：见 2.5 汇总表最后一列；无"待定"项。
4. **每条 Phase 项有代价量级**：标注为改代码 / 改配置 / 新增模块 / 改部署。
5. **排除误报**：G12 明确记录出站 SSRF 防护已生效，避免把"已正确"误列为待补。
6. **不越界**：本文不含代码改动，不含对既有文档的修改；偏差集中在第 4 节并可独立提交。

### 5.3 建议的下一步

1. 就 Phase 0 的 P0-1 ~ P0-8 逐项开票，其中 **P0-1、P0-2、P0-3 三件是"多租户上线"的硬前置**（三者共同消除跨租户可达性）。
2. 第 4 节的 D1-D7 作为独立文档修正提交（D1、D3、D4 涉及"文档声称存在但代码没有"的能力，优先级最高，因为会误导后续开发者）。
3. Phase 1 的 P1-1（workspace 契约）先行，因为它的产出是 P1-2/P1-3 的验收依据。
